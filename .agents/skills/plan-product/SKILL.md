# 产品规划与MVP定义

## 目标

将经过初步澄清的产品概念转化为结构清晰、范围可控、能够分阶段验证的产品规划。

重点回答：

- 产品要围绕什么目标和原则建设。
- 哪条用户旅程和价值闭环最重要。
- 产品需要哪些能力和模块。
- 第一阶段必须做什么、明确不做什么。
- 功能如何排序和分期。
- 每个阶段验证什么判断。

最终交付物默认为《产品规划方案 V0.5》。它用于确认产品架构、MVP和阶段范围，不是研发执行型PRD。

## 工作边界

本Skill负责：

- 产品目标和规划原则。
- 用户、购买者、决策者、运营者等角色关系。
- 核心用户旅程和价值闭环。
- 产品能力地图和模块架构。
- MVP、Demo、试点和正式版本的范围区分。
- 功能优先级和版本分期。
- 概念级数据、AI、运营和系统依赖。
- 阶段验证指标、风险和进入下一阶段的条件。

本Skill不默认负责：

- 页面原型和完整交互细节。
- 字段、校验和计算公式。
- 详细状态流转和权限矩阵。
- 接口参数、错误码和数据库设计。
- 完整异常规则和验收标准。
- 研发工期和人员排期承诺。

用户明确要求上述内容时，只补充当前规划决策所必需的部分，并建议进入功能方案或执行型PRD工作流。

## 基本原则

1. 让模块服务于用户价值和产品目标，不按页面或部门机械拆分。
2. 先确定核心旅程和价值闭环，再设计模块架构。
3. 让MVP验证最关键假设，不把MVP理解为完整产品的缩小版。
4. 同时评估用户价值、业务价值、使用复杂度、运营成本、开发复杂度和验证成本。
5. 保持创新性，但不以功能堆叠、视觉包装或技术标签代替创新。
6. 对未经验证的内容标记假设，不把概念型判断升级为确定事实。
7. 不在缺少资源和技术依据时制造精确排期、成本或指标。
8. 明确非本期范围，防止规划在讨论中无限扩张。
9. 每个阶段都要说明目标、范围、依赖和验证方式。
10. 保持项目事实隔离，只复用方法和协作偏好。

## 工作流程

### 1. 读取规划输入

按需读取：

- 当前项目最新的概念型PRD、产品说明或已确认决策。
- 当前项目的用户、业务、品牌、战略、技术和合规资料。
- 用户提供的访谈、数据、市场分析和约束。
- `context/collaboration-preferences.md`，若文件存在。

只读取与当前规划直接相关的材料。历史案例和其他产品只能用于参考方法和结构，不得作为当前项目事实。

先提取并区分：

- 已确认事实。
- 已确认决策。
- 当前假设。
- 外部证据。
- 约束与依赖。
- 待确认项。

### 2. 执行规划成熟度检查

开始模块和MVP规划前，至少检查：

1. 首要用户是谁。
2. 核心场景和问题是什么。
3. 产品提供什么独特结果。
4. 核心价值机制是什么。
5. 用户、购买者和决策者之间是什么关系。
6. 当前最需要验证的产品假设是什么。
7. 已知的业务、资源、技术、数据、运营和合规约束是什么。

将成熟度判断为：

- **不可规划**：目标用户、核心问题或价值主张仍然模糊。
- **假设型规划**：概念基本成立，但关键判断缺少证据。
- **可评审规划**：定位、价值和核心机制已经明确，可以讨论架构与MVP。
- **可进入方案设计**：架构、MVP、优先级和阶段边界已经确认。

若不可规划，停止扩展模块，优先返回 `product-concept-discovery` 补齐关键问题。

若属于假设型规划，可以继续输出草案，但必须标记：

- 当前规划成熟度。
- 不能直接作为研发承诺的部分。
- 需要优先验证的假设。
- 验证失败后受影响的模块和阶段。

### 3. 建立规划基线

用简洁结构确认：

```markdown
### 规划基线
- 产品定义：
- 首要用户：
- 核心场景：
- 用户价值：
- 业务价值：
- 核心机制：
- 当前阶段：
- 关键约束：
- 关键假设：
```

发现概念文档与最新要求冲突时，指出冲突并以最新确认内容为准。不要默默混合多个版本。

### 4. 定义产品目标与产品原则

定义少量、能够指导取舍的产品目标。目标应描述希望产生的结果，不直接写成功能清单。

根据当前产品特征形成3至5条产品原则，例如：

- 用户优先获得价值，再要求提供更多信息。
- 高频主路径保持短而明确。
- 系统承担复杂处理，前台减少选择和输入。
- 高风险动作保留人工确认和兜底。
- 第一阶段优先证明核心闭环，不追求模块齐全。

产品原则必须能够用于拒绝不合适的功能。避免“体验友好”“智能便捷”等无法指导决策的口号。

### 5. 明确用户与价值关系

识别适用角色：

- 使用者。
- 直接受益者。
- 购买者或资源投入者。
- 决策者。
- 管理员或运营者。
- 内容、数据或服务提供者。
- 其他关键合作方。

对每个关键角色说明：

- 想完成什么任务。
- 提供什么资源、数据或行为。
- 获得什么结果。
- 为什么愿意持续参与。
- 与其他角色如何形成价值交换。

角色较多时，优先确定首要用户和第一阶段必须服务的角色。不要为了显示平台完整而同时满足所有角色。

### 6. 设计核心用户旅程与价值闭环

先形成最短核心旅程：

```text
触发或入口
→ 用户采取关键行动
→ 系统/服务完成核心处理
→ 用户获得直接结果
→ 用户或业务采取下一行动
→ 产品沉淀持续价值
```

检查：

- 用户第一次为什么进入。
- 多快能够感受到价值。
- 哪个动作构成核心转化。
- 结果是否能够进入真实业务或生活场景。
- 用户为什么再次使用；若不需要复用，项目如何持续创造价值。
- 组织如何获得可观察的业务结果。

旅程存在明显断点时，先修复闭环，再增加模块。

### 7. 选择产品架构方式

根据产品特征选择主要组织方式：

- **用户旅程型**：围绕连续任务和使用阶段组织。
- **核心能力型**：围绕可复用的产品能力组织。
- **角色工作台型**：不同角色具有明显不同目标和流程。
- **平台生态型**：多方参与、资源交换和规则治理是核心。
- **内容或服务型**：内容供给、匹配、消费和反馈构成主链路。
- **设备或跨系统型**：设备状态、连接和系统协作决定结构。

可以组合两种方式，但必须指定主架构，避免同时按角色、页面、流程和部门重复拆分。

若存在真正影响方向的架构分歧，先给出2至3个候选方案，并比较：

| 维度 | 说明 |
|---|---|
| 用户价值 | 是否更快完成核心任务 |
| 业务价值 | 是否形成清晰业务结果 |
| 创新与差异化 | 是否产生实质改善 |
| 使用复杂度 | 用户需要多少步骤、判断和输入 |
| 运营成本 | 内容、配置和人工维护负担 |
| 开发复杂度 | 系统、数据、接口和技术依赖 |
| 验证能力 | 是否能验证核心假设 |
| 风险 | 最大失败点和不可控因素 |

给出推荐方向和条件性理由，不用多个相似方案制造选择。

### 8. 建立产品能力地图与模块架构

先定义能力，再聚合为模块。

将能力按需分为：

- **核心价值能力**：直接产生用户承诺结果。
- **闭环承接能力**：让结果进入后续行动或业务流程。
- **增长与持续使用能力**：支持触达、复用、留存或传播。
- **运营与管理能力**：支持配置、审核、内容和人工处理。
- **数据与智能能力**：支持采集、分析、推荐、生成和监控。
- **平台基础能力**：账户、权限、安全、日志和系统协作。

每个模块至少说明：

- 模块名称。
- 服务的角色与场景。
- 解决的问题。
- 提供的核心能力。
- 在价值闭环中的位置。
- 与其他模块的输入输出关系。
- 是否进入MVP。

模块名称应表达用户或业务能力，不要只使用页面名称。一个模块无法说明价值和闭环位置时，重新判断是否需要存在。

### 9. 定义MVP范围

先区分：

- **概念原型**：验证理解和体验方向，可以不真实运行。
- **Demo**：证明核心故事或能力，可以使用模拟数据和人工流程。
- **MVP**：让真实目标用户完成核心任务并验证价值假设。
- **试点版**：在受控真实环境中验证运营、协作、风险和规模条件。
- **正式版本**：满足稳定运营、治理和扩展要求。

为当前阶段明确选择一种交付形态，不混用概念。

MVP必须说明：

- 要验证的核心假设。
- 首要用户和核心场景。
- 必须走通的端到端旅程。
- 必须真实成立的能力。
- 可以模拟、人工完成或暂缓的部分。
- 明确不做的功能和角色。
- 成功、失败和停止投入的判断信号。

判断功能是否进入MVP时，依次检查：

1. 没有它，核心旅程能否完成？
2. 没有它，核心假设能否验证？
3. 它是否只是为了让产品看起来完整？
4. 能否用人工、配置、模拟或外部工具暂时代替？
5. 它带来的学习价值是否高于建设成本？

### 10. 确定优先级

优先级判断至少考虑：

- 对核心用户价值的贡献。
- 对业务目标的贡献。
- 对关键假设验证的贡献。
- 风险降低作用。
- 前置依赖关系。
- 用户、运营和开发复杂度。
- 当前证据强度。

优先采用定性分级：

- **P0 / 必须**：缺失后核心旅程或验证无法成立。
- **P1 / 重要**：显著改善价值、效率或风险，但可以稍后补充。
- **P2 / 增强**：优化体验、运营或增长，不影响第一阶段成立。
- **暂缓 / 淘汰**：价值不足、成本过高、依赖未满足或偏离目标。

只有在数据可信且比较对象一致时才使用RICE、ICE等数字模型。不得通过虚构覆盖人数、转化率或工作量制造精确排序。

### 11. 制定版本分期与路线图

每个阶段至少说明：

| 项目 | 内容 |
|---|---|
| 阶段目标 | 本阶段要证明或实现什么 |
| 核心假设 | 依赖哪些尚未确认的判断 |
| 用户与场景 | 服务谁、在哪个场景使用 |
| 范围 | 包含哪些能力和模块 |
| 非范围 | 明确排除什么 |
| 关键依赖 | 数据、系统、内容、合作方和资源 |
| 验证方式 | 用什么行为、反馈或指标判断 |
| 进入条件 | 何时进入下一阶段 |

路线图以目标和验证结果驱动，不默认使用固定日期。

用户明确要求时间计划时，区分：

- 已知期限。
- 基于资源确认的排期。
- 暂定时间窗口。
- 尚未评估的工作。

不得把未经研发和资源负责人确认的时间写成承诺。

### 12. 审查AI、数据与运营闭环

当规划包含AI能力时，至少说明：

- 输入数据或内容从哪里来。
- AI替代或增强哪个传统流程。
- 输出由谁使用。
- 输出如何进入下一业务动作。
- 错误、不确定或不可用时如何处理。
- 是否需要人工审核或确认。
- 不使用AI时是否存在更简单可靠的方案。

当规划依赖持续运营时，至少说明：

- 谁负责配置、内容、审核和维护。
- 需要多高频率更新。
- 运营成本是否可承受。
- 冷启动和供给不足如何处理。

当规划涉及跨系统或第三方能力时，只定义业务依赖、数据方向和时效要求，不擅自承诺接口存在或指定技术实现。

### 13. 完成规划风险审查

按需检查：

- 用户需求是否真实。
- 产品定位是否过宽。
- MVP是否试图验证太多事情。
- 模块是否重复或缺少主次。
- 核心旅程是否存在断点。
- 使用动机和付费动机是否混淆。
- 运营成本是否被低估。
- 是否依赖不可控的合作方、数据或系统。
- AI是否只有展示价值，没有业务闭环。
- 是否涉及隐私、安全、合规或高风险专业判断。

发现重大风险时，指出受影响的阶段和应采取的验证、降级或退出措施。

### 14. 形成下一步决策

规划完成后，明确推荐：

- 返回概念发现继续澄清。
- 开展用户研究或市场分析。
- 制作概念原型或Demo。
- 进入某个重点模块的功能方案设计。
- 形成执行型PRD。
- 暂停或终止当前方向。

不要默认所有规划都应立即进入开发。

## 对话与协作方式

遵循以下默认节奏：

1. 简短复述规划基线和成熟度。
2. 提供一个可修改的初步架构，必要时提供2至3个差异明确的方案。
3. 每轮只询问3至5个最影响目标、架构、MVP或分期的问题。
4. 根据用户反馈更新共识、假设、范围和优先级。
5. 用户确认主要方向后再形成完整规划文档。

用户要求先看草案时，可以直接输出假设型规划，并清楚标记假设和不可直接执行的部分。

用户认为方案“传统”“复杂”“普通”或“鸡肋”时，不要只修改模块名称或视觉表现。重新检查用户价值、使用场景、价值闭环、AI必要性和复杂度。

用户只要求规划某个模块、MVP或路线图时，只输出该部分及必要上下文，不强制生成整份文档。

## 《产品规划方案 V0.5》结构

根据项目复杂度选择必要章节，不为填满模板而编造信息。

1. **文档信息**：产品/项目名称、V0.5版本、规划成熟度、日期、责任人、输入文档及本版目标。
2. **执行摘要**：产品目标、推荐架构、MVP范围、最大假设和当前建议。
3. **规划基线**：产品定义、首要用户与场景、用户与业务价值、已确认决策、关键假设和约束。
4. **产品目标与产品原则**：阶段目标、非目标以及3至5条能够指导取舍的原则。
5. **用户、角色与价值关系**：角色定义、各角色的任务投入与结果、首要角色与后续角色。
6. **核心用户旅程与价值闭环**：端到端旅程、关键转化点、持续用户价值和业务闭环。
7. **产品架构**：架构方式、必要的候选方案比较、推荐架构及理由。
8. **产品能力地图与模块规划**：能力分层、模块职责、模块关系和优先级。
9. **MVP定义**：MVP类型与核心假设、必须走通的旅程、必须真实成立的能力、可模拟部分、范围与非范围。
10. **优先级与取舍**：P0、P1、P2、暂缓项、依赖关系以及主要取舍理由。
11. **版本分期与路线图**：各阶段目标、范围、非范围、关键依赖、验证方式和进入条件。
12. **数据、AI、运营与系统依赖**：只保留当前产品适用的内容。
13. **风险与开放问题**：重大风险、影响阶段、缓解或验证措施、待确认责任人。
14. **验证指标与阶段决策**：核心行为或结果信号、观察周期、继续、调整或停止的判断方式。
15. **下一步行动**：下一项研究、原型、方案或文档，以及已知的责任人和前置输入。

## 输出要求

- 默认使用中文，结论优先，结构清晰。
- 重要内容按“已确认 / 假设 / 待验证”区分。
- 先说明推荐架构和MVP，再展开细节。
- 模块描述必须包含价值、角色、能力和闭环位置。
- 方案比较必须给出实质差异、取舍和推荐条件。
- 图示能显著提升理解时，使用简洁的旅程图、能力图或模块关系图。
- 不制造精确市场数据、指标目标、开发成本和排期。
- 不把概念规划写成宣传方案，也不把模块清单写成产品规划。
- 不为显示完整而加入与核心目标无关的功能。
- 不提前替设计、研发、测试和运营作出缺乏依据的专业承诺。

## 质量检查

输出前确认：

1. 规划是否与产品概念、用户问题和价值主张一致。
2. 是否明确一个首要用户和一条核心旅程。
3. 产品原则是否能够指导功能取舍。
4. 模块是否按能力和价值划分，而不是页面堆叠。
5. MVP是否验证关键假设，而不是追求功能齐全。
6. 是否明确MVP范围和非范围。
7. 优先级是否有依据并考虑依赖。
8. 每个阶段是否有目标、范围和验证方式。
9. AI、数据和运营是否形成可执行闭环。
10. 是否遗漏重大业务、技术、数据、隐私或合规依赖。
11. 是否区分事实、假设和待验证内容。
12. 是否过早进入了执行型PRD细节。

## 与其他Skill衔接

- 定位、首要用户、核心问题或价值主张仍不清晰时，使用 `product-concept-discovery`。
- 关键用户需求缺少证据时，进入用户研究或需求验证工作流。
- 需要核实市场空间、竞品和替代方案时，进入市场分析工作流。
- 规划确认后，选择一个P0模块进入功能方案设计。
- 目标、范围、流程和业务规则已经确认后，进入执行型PRD工作流。

本Skill只负责把产品概念转化为可决策的产品架构、MVP和阶段规划，不替代后续详细需求设计。
