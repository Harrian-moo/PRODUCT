# UI 设计审查与改进建议

## 目标

以专业 UI 设计师的视角审视产品页面和交互方案，找出用户可能感知到但说不清的问题，并给出具体、可执行的修改建议。

重点回答：

- 用户第一眼看到的是什么？是否符合产品想让用户先看到的东西？
- 每个页面的信息层级是否清晰——用户不需要思考就知道该看哪、该点哪？
- 移动端和网页端需要不同的处理——拇指能不能够到？触控目标够不够大？
- 同一类型的交互在不同页面是否一致——别让用户每次都要重新学习？
- 色彩、字体、间距是否形成了清晰的层级而非混乱堆叠？
- 空状态、加载中、错误状态在视觉上是否被忽略了？

最终交付物为《UI 设计审查报告》，是一份文字建议清单，不是视觉稿。

## 工作边界

本 Skill 负责：

- 审查页面描述、ASCII 线框图、可交互原型或已有设计截图（通过 OCR 或描述）。
- 从信息层级、视觉焦点、交互一致性、触控适配、色彩字体、状态完整性六个维度分析。
- 给出具体的修改建议（如"这个按钮从 32px 放大到 44px""把三个入口的间距统一为 16px"）。
- 区分移动端和网页端的设计建议。
- 标注严重度（影响可用性 / 影响体验 / 纯建议）。

本 Skill 不负责：

- 生成视觉设计稿或图片。
- 制定完整的设计系统或组件库。
- 替代可用性测试或用户研究。
- 像素级标注——不精确到具体的十六进制色值或字号像素值（除非已有设计规范）。
- 替代真正的 UI 设计师对品牌调性的判断。

## 基本原则

1. 设计审查不是审美评判——每条意见必须指向"用户会因此遇到什么问题"。
2. 移动端和网页端是两种设计语言——不同时适用同一条规则。
3. 信息层级是最核心的问题——用户花 2 秒扫一眼，应该知道该看哪。
4. 一致性比好看更重要——不统一的间距比不好看的颜色更伤体验。
5. 空状态和错误状态是设计的二等公民——但用户遇到它们的频率可能比正常状态还高。
6. 建议要具体到可以动手改的程度——不说"交互不够友好"，说"这个按钮太小，建议从 32px 改为 44px"。

## 工作流程

### 1. 确认审查对象和端侧

- **端侧**：移动端（微信小程序 / APP）还是网页端（管理后台 / PC 端）？
- **审查范围**：单个页面、完整流程、还是整个模块？
- **输入形式**：文字描述 / ASCII 线框图 / 原型 HTML / 截图描述？
- **已有设计规范**：是否有既定的色彩、字体、间距规范？（没有则按通用原则审查）

### 2. 分维度审查

#### 维度 1：信息层级

| 检查项 | 移动端 | 网页端 |
|--------|:--:|:--:|
| 用户 2 秒内第一眼看到的是什么 | ✅ | ✅ |
| 核心操作是否在视觉上最突出 | ✅ | ✅ |
| 次要信息是否有被当作主信息的风险 | ✅ | ✅ |
| 页面是否有清晰的上中下或左中右层次 | ✅ | ✅ |
| 不同模块之间的视觉权重是否有主次 | ✅ | ✅ |
| 信息密度是否适合当前端侧 | 低密度优先 | 可适度高密度 |

#### 维度 2：视觉焦点与引导

| 检查项 | 说明 |
|--------|------|
| 核心 CTA（行动号召按钮）是否在视觉上不可忽略 | 位置 + 大小 + 颜色 |
| 是否有干扰用户完成主任务的视觉噪音 | 无用的装饰、过多的色彩、不必要的图标 |
| 视觉流是否符合阅读习惯 | 移动端：从上到下；网页端：从左到右 + 从上到下 |
| 是否有"不知道该看哪"的区域 | 多个同等权重的元素挤在一起 |

#### 维度 3：触控与交互（移动端专用）

| 检查项 | 标准 |
|--------|------|
| 可点击元素的最小尺寸 | ≥ 44×44px（微信小程序规范） |
| 点击区域之间的最小间距 | ≥ 8px，避免误触 |
| 关键按钮是否在拇指热区 | 屏幕下半部分单手可达 |
| 滑动手势是否与系统手势冲突 | 如横向滑动 vs 页面返回 |
| 是否有触控反馈 | 点击时有视觉变化（缩放/变色/阴影） |

#### 维度 4：交互一致性

| 检查项 | 说明 |
|--------|------|
| 同类操作的按钮样式是否一致 | 所有"确认"按钮是否同色同大小 |
| 同类页面的返回方式是否一致 | 左上角返回 / 底部 Tab / 手势 |
| 弹窗的关闭方式是否一致 | 右上 ✕ / 点击遮罩 / 下拉关闭 |
| Toast/提示的出现位置和时长是否一致 | |
| 列表项的交互模式是否一致 | 点击进入详情 vs 点击勾选 vs 点击展开 |

#### 维度 5：色彩与字体

| 检查项 | 说明 |
|--------|------|
| 主色/辅色/中性色是否有明确分工 | 主色 = 品牌 + 核心操作；辅色 = 标签/状态 |
| 文字是否有至少 3 个层级 | 标题 / 正文 / 辅助文字（大小 + 灰度区分） |
| 色彩对比度是否满足可读性 | 浅色文字在浅色背景上是否看得清 |
| 是否有仅靠颜色传达信息的场景 | 如红色=错误——需加图标或文字作为备用方式 |
| 品牌色占比是否合理 | 不要满屏都是品牌色 |

#### 维度 6：状态完整性

| 检查项 | 说明 |
|--------|------|
| 是否有加载中状态的设计 | 首次加载 / 刷新 / 提交中的视觉反馈 |
| 是否有空状态的设计 | 无数据时的引导（不只是"暂无数据"四个字） |
| 是否有错误状态的设计 | 网络错误、权限不足、操作失败 |
| 是否有不可用状态的设计 | 按钮置灰、功能锁定 |
| 是否有完成/成功状态的设计 | 操作完成后的确认反馈 |

### 3. 标注问题严重度

| 等级 | 定义 | 示例 |
|:--:|------|------|
| 🔴 阻塞 | 用户无法完成核心任务或会频繁出错 | 核心按钮尺寸 < 32px、手机端无法单手操作 |
| 🟡 影响体验 | 用户能完成任务但有明显不适 | 不一致的间距、次要信息喧宾夺主 |
| 🟢 优化建议 | 做不做都行，做了更好 | 动画细节、微交互、空状态插图 |

### 4. 输出审查报告

```markdown
## UI 设计审查报告

### 基本信息
- 审查对象：XXX 模块 / XXX 页面
- 端侧：移动端 / 网页端
- 审查范围：X 个页面 / X 个流程

### 总体评估
（1-2 句总结：最大的设计问题和最大的设计亮点）

### 问题清单

| # | 位置 | 维度 | 严重度 | 问题 | 建议 |
|:--:|------|------|:--:|------|------|
| 1 | 主页面热量卡片 | 信息层级 | 🔴 | 三个数值等大等色，用户分不清重点 | 剩余热量放大 1.5 倍 + 品牌色 |
| 2 | 拍照按钮 | 触控 | 🔴 | 44px 的相机按钮与 32px 的餐别按钮并列 | 统一为 44px，或加大间距 |
| ... | ... | ... | ... | ... | ... |

### 移动端专项建议
### 网页端专项建议
### 下一步
```

## 输出要求

- 默认中文。
- 每条建议具体到"在哪个页面/哪个位置，改什么，改成什么"。
- 严重度标注和理由缺一不可。
- 不输出泛泛的"整体设计不够精致""需要提升用户体验"。
- 不编造不存在的设计问题。

## 质量检查

1. 是否区分了移动端和网页端的不同建议。
2. 每条问题是否定位到具体位置和具体维度。
3. 是否有至少一条 🔴 或 🟡（如果没有，是设计真的完美还是审查不够细）。
4. 建议是否具体到可以动手改。
5. 是否覆盖了空状态和错误状态的检查。
6. 是否避免了审美式的主观评判。

## 与其他 Skill 衔接

- 接受 PRD 中的页面描述、ASCII 线框图、`build-prototype` 生成的 HTML 原型作为输入。
- 审查建议可用于修改 PRD 中的页面交互描述，也可直接用于指导 `build-prototype` 重新生成。
- 发现系统性问题（如"所有弹窗的关闭方式不一致"）时，可汇总为设计规范建议。
- 本 Skill 不替代真正的 UI 设计师评审，但可在交付设计稿前做第一轮自检。
