# 管理后台需求规范

本规范供 `write-prd` 在撰写管理后台、运营后台、配置后台或内部工作台需求时按需读取。重点面向消费端产品的配套管理能力，例如内容运营、AI配置、活动权益、用户与会员、规则策略、审核处置和数据运营。

它是专项需求指南，不是固定模板。只使用与当前产品、角色、风险和版本范围有关的部分，不为覆盖清单而增加功能。

## 使用方式与适用边界

当需求出现以下任一特征时，读取本规范：

- 操作对象主要是运营、审核、客服、内容、数据或管理员。
- 产品需要配置内容、活动、权益、规则、推荐位、AI能力或系统参数。
- 需求包含列表、筛选、表单、批量处理、导入导出、审核或发布。
- 需要定义组织、角色、功能权限、数据权限或敏感操作权限。
- 需要记录操作历史、版本、发布结果或责任人。
- 消费端功能依赖后台配置、人工审核或运营维护。

以下情况不要把本规范当作完整解决方案：

- 产品定位、功能价值或核心流程仍未确认，先返回上游方案工作流。
- 只是服务端技术架构、数据库或运维控制台，不属于产品后台PRD。
- 涉及复杂系统对接和数据同步时，使用 `define-interface-requirement`。
- 用户只要求审查已有后台PRD时，使用 `review-requirement`。

按任务深度选择：

- **单点修改**：只读取受影响的页面、权限、规则、历史数据和验收部分。
- **单模块后台**：读取需求基线、角色权限、业务对象、页面模式、异常和验收。
- **完整运营后台**：读取全部适用章节，先设计业务对象、流程与权限，再写页面。
- **专项需求**：用户只要求内容、AI、活动、权益、审核、导入导出或数据看板时，只读取相应章节及必要的权限、日志和发布要求。

## 后台需求基线

管理后台不是消费端页面的简单镜像。开始撰写前，先明确：

```markdown
### 后台需求基线
- 服务的前台产品/业务：
- 后台建设目的：
- 主要使用角色：
- 角色需要完成的任务：
- 当前操作方式与问题：
- 需要管理的业务对象：
- 后台操作如何影响前台用户：
- 本期范围：
- 非本期范围：
- 数据、安全和合规约束：
- 运营维护频率与规模：
- 已确认事实：
- 假设与待确认项：
```

后台目标应描述业务结果，例如：

- 降低内容发布错误和人工沟通成本。
- 让运营能够独立配置活动并安全回滚。
- 让审核人员在统一队列中处理高风险内容。
- 让产品能够追踪AI策略版本和实际生效范围。

不要把“增加后台页面”“支持增删改查”写成最终目标。

### 前后台责任关系

每项后台能力说明：

- 后台管理什么业务对象。
- 哪些配置会影响前台展示、推荐、资格或流程。
- 修改后何时生效，影响哪些用户、版本、渠道或地区。
- 前台已经产生的数据是否会被追溯修改。
- 后台失败、延迟或配置错误时，前台怎样降级。
- 是否需要用户感知、运营通知或人工补救。

## 角色、组织与权限

### 识别角色

根据当前业务识别实际角色，例如：

- 超级管理员。
- 产品或系统管理员。
- 运营人员。
- 内容编辑。
- 审核人员。
- 客服或人工处理人员。
- 数据分析人员。
- 只读查看者。
- 外部合作方。

不要默认所有项目都需要这些角色。角色应来自真实职责，而不是为了填满权限表。

### 区分四类权限

1. **菜单与页面权限**：能否进入某模块或页面。
2. **操作权限**：能否创建、编辑、删除、审核、发布、导出或回滚。
3. **数据权限**：能查看和操作哪些组织、产品、渠道、地区、用户或本人创建的数据。
4. **字段权限**：敏感字段能否查看、编辑、导出或仅显示脱敏值。

页面隐藏不能替代真正的权限控制。PRD要定义业务权限结果，具体鉴权实现由研发负责。

### 角色权限矩阵

复杂后台使用：

| 业务对象/操作 | 角色 | 查看范围 | 创建 | 编辑 | 删除 | 审核 | 发布 | 导出 | 特殊条件 |
|---|---|---|---|---|---|---|---|---|---|
| | | | | | | | | | |

每个权限项同时检查：

- 对象归属发生变化后权限是否同步。
- 人员离职、转岗或角色撤销后如何处理。
- 临时授权是否有有效期和审批。
- 高风险权限是否允许角色自行授予自己。
- 同一人是否可以同时提交和审核。
- 外部合作方能否越过组织或产品边界。
- 批量操作和导出是否需要更高权限。
- 无权限、权限过期和权限变更时怎样提示。

### 数据范围

数据范围按项目实际选择：

- 全部数据。
- 所属组织或团队。
- 指定产品、业务线、渠道、地区或租户。
- 本人创建、本人负责或分配给本人的数据。
- 仅脱敏数据。

同一角色可能在不同对象上拥有不同数据范围，不要只定义一个笼统的“管理员权限”。

## 业务对象与生命周期

后台设计先定义对象，再设计页面。

### 业务对象清单

| 对象 | 业务含义 | 唯一标识 | 创建来源 | 维护角色 | 主要状态 | 前台影响 | 保留/删除规则 |
|---|---|---|---|---|---|---|---|
| | | | | | | | |

典型对象可能包括内容、栏目、标签、活动、任务、权益、会员方案、规则、提示词、知识条目、审核单、反馈单和配置版本，但必须服从当前项目事实。

### 对象关系

说明：

- 一对一、一对多或多对多关系。
- 父子对象、组合对象和引用关系。
- 删除或失效上级对象时，下级对象如何处理。
- 对象被活动、页面、规则或用户记录引用时能否删除。
- 复制对象时复制哪些内容，不复制哪些历史数据。
- 对象名称变化是否影响历史记录。

对象达到三个以上且关系复杂时，提供业务对象关系图。

### 生命周期和状态

对具有发布、审核、启停或处理过程的对象建立状态表：

| 当前状态 | 触发事件 | 前置条件 | 操作角色 | 下一状态 | 前台影响 | 失败处理 |
|---|---|---|---|---|---|---|
| | | | | | | |

按需覆盖：

- 草稿、待审核、审核通过、审核拒绝。
- 待发布、已发布、已暂停、已下线。
- 待生效、生效中、已过期、已失效。
- 待处理、处理中、已解决、已关闭。

状态名称和数量必须来自真实业务。明确每个状态允许查看、编辑、删除、复制、审核、发布、撤回和回滚哪些操作。

## 信息架构与工作入口

### 模块划分

按业务任务和对象划分模块，不按照数据库表、接口或前台页面逐一复制。

每个模块说明：

- 服务角色和核心任务。
- 管理的对象和业务结果。
- 与前台功能的关系。
- 入口、主要操作和后续去向。
- 与其他后台模块的依赖。

识别并避免：

- 同一对象分散在多个菜单中重复维护。
- 页面名称相似但职责不清。
- 为每个动作单独建立菜单。
- 操作完成后没有下一步或无法追踪结果。

### 工作台和待办

角色存在高频任务、审核队列或异常处理时，考虑工作台：

- 今日待处理。
- 待审核、待发布和发布失败。
- 即将开始、即将结束和已过期配置。
- 异常数据、失败任务和风险告警。
- 最近操作、常用入口和本人负责对象。

工作台只聚合可行动信息，不把所有统计数据堆成首页。

### 导航与上下文

明确：

- 菜单层级和模块名称。
- 面包屑、返回和跨对象跳转。
- 从列表进入详情、编辑、审核和日志的路径。
- 多产品、多组织、多环境切换时的当前上下文。
- 切换上下文后筛选条件、草稿和未保存内容如何处理。

## 通用页面与操作模式

### 列表页

列表页至少定义：

| 维度 | 需要说明 |
|---|---|
| 入口与权限 | 哪些角色可以进入和查看 |
| 数据范围 | 默认展示哪些数据 |
| 列表字段 | 名称、含义、来源、格式、空值和脱敏 |
| 默认排序 | 排序字段和方向 |
| 筛选 | 条件、组件、默认值、组合规则 |
| 搜索 | 搜索对象、匹配方式和大小写规则 |
| 分页 | 分页方式、每页数量或待研发确认 |
| 行操作 | 显示和可用条件 |
| 批量操作 | 勾选范围、上限、权限和结果反馈 |
| 空与异常 | 无数据、无结果、加载失败和无权限 |

额外检查：

- 默认筛选是否会让用户误以为数据缺失。
- 多条件之间是“且”还是“或”。
- 时间筛选使用创建、修改、生效还是发布时间。
- 列表状态与详情状态是否一致。
- 操作后是否保持筛选、分页和滚动位置。
- 是否需要列显示配置、固定列或保存筛选方案。

### 详情页

说明：

- 基础信息、状态、关联对象和操作记录。
- 当前角色可见和可编辑的字段。
- 不同状态下可执行的操作。
- 从详情跳转到相关内容、用户、活动或配置的路径。
- 历史版本、发布记录和审核意见入口。
- 敏感信息展示和复制限制。

详情页用于理解对象全貌，不应只是把列表字段竖向排列。

### 新增与编辑表单

字段表使用：

| 字段 | 业务含义 | 类型/组件 | 必填条件 | 默认值 | 取值/枚举 | 校验 | 权限 | 联动 | 保存结果 |
|---|---|---|---|---|---|---|---|---|---|
| | | | | | | | | | |

按需定义：

- 新增与编辑字段是否一致。
- 字段何时显示、禁用、清空或重新计算。
- 修改已发布对象时是直接生效、生成草稿还是创建新版本。
- 自动保存、草稿和离开页面提醒。
- 服务端校验失败时的字段定位和已填内容保留。
- 多人编辑、版本过期和提交冲突。
- 保存、保存并继续、保存并提交审核的差异。

不要写“填写信息后保存到数据库”。应说明保存成功后的对象状态、页面反馈、前台影响和后续动作。

### 新增、编辑、复制和删除

分别说明：

- 入口和权限。
- 可操作状态。
- 前置校验和关联对象影响。
- 成功后的状态、反馈和列表变化。
- 失败后的数据结果和恢复方式。
- 是否记录操作人、时间、原因和修改内容。

删除需要区分：

- 物理删除。
- 逻辑删除。
- 停用、下线或归档。

优先定义业务结果，不擅自指定技术删除方式。对象已有历史使用记录或被其他对象引用时，通常不应直接消失。

### 批量操作

明确：

- 选择范围是当前页、全部搜索结果还是手动上传名单。
- 选择数量和数据量上限。
- 不同状态对象能否混合处理。
- 操作前的校验、预估和二次确认。
- 全部成功、全部失败和部分成功反馈。
- 失败项下载、重试和恢复方式。
- 是否异步执行，用户在哪里查看进度。
- 是否允许取消，取消后已完成部分如何处理。
- 批量操作的日志、审计和通知。

### 导入

导入需求至少包含：

- 模板版本、下载入口和字段说明。
- 文件类型、大小、行数、编码和工作表要求。
- 必填、格式、枚举、唯一性和关联对象校验。
- 重复数据是拒绝、覆盖、跳过还是合并。
- 校验是整批阻断还是允许部分成功。
- 预检查、确认导入和正式写入的流程。
- 处理进度、成功数量和失败数量。
- 失败行、原因和修正后的重新导入。
- 重复上传、网络中断和任务超时。
- 导入记录、操作人和结果保留时间。

不只描述“支持Excel导入”。

### 导出

导出需求至少包含：

- 导出范围：当前页、筛选结果、选中项或全部。
- 导出字段、顺序、格式、枚举翻译和时间口径。
- 敏感字段脱敏、审批和权限。
- 大数据量异步导出、进度和下载入口。
- 文件有效期、下载次数和访问控制。
- 无数据、部分失败、超时和重复导出。
- 导出任务和下载日志。

页面展示字段不等于默认全部可导出。

## 内容与资源运营

适用于文章、音视频、课程、卡片、话题、标签、栏目和运营素材等对象。

按需定义：

- 内容类型、来源、归属和版权信息。
- 标题、摘要、正文、封面、附件和适用人群。
- 分类、标签、栏目和关联内容。
- 草稿、预览、审核、定时发布、下线和归档。
- 多端展示差异和客户端版本兼容。
- 排序、置顶、推荐位和有效期。
- 内容修改是否生成新版本，已发布内容如何回滚。
- 敏感词、风险内容和人工审核。
- 内容失效、资源删除和外部链接不可用。
- 发布后指标和用户反馈入口。

运营位和推荐位额外说明：

- 展示位置、尺寸、数量和端。
- 投放对象、渠道、地区和用户范围。
- 开始与结束时间。
- 优先级、互斥、兜底和冲突处理。
- 点击行为、落地页和无效链接处理。
- 预览、灰度、监控和紧急下线。

## AI、提示词与知识库管理

涉及AI运营后台时，不把“可配置模型和提示词”作为完整需求。

### AI能力对象

识别并区分：

- AI能力或场景。
- 模型和供应方配置。
- 系统提示词、模板和变量。
- 知识库、文档、切片和数据源。
- 安全策略、审核规则和人工兜底。
- 测试样本、评测结果和线上反馈。

### 提示词与策略

定义：

- 使用场景、输入变量和输出要求。
- 适用产品、端、版本、人群或灰度范围。
- 草稿、测试、审核、发布、停用和回滚。
- 版本号、修改原因、差异和责任人。
- 发布前测试样本、预期结果和风险用例。
- 多条策略命中时的优先级和兜底。
- 模型超时、不可用、限流和结果不合格时的降级。
- 是否允许运营查看或修改敏感系统提示词。

### 知识库

定义：

- 数据来源、授权、负责人和更新频率。
- 文档上传、解析、切片、索引和生效状态。
- 支持的文件、大小和内容类型。
- 重复文档、版本更新、删除和历史引用。
- 解析失败、索引失败和部分成功。
- 知识适用范围、优先级和过期时间。
- 内容检索、预览、测试和问题定位。
- 敏感信息、访问权限和删除要求。

产品经理定义业务结果和运营流程，不在没有技术依据时规定切片算法、向量模型和技术参数。

### AI输出审核与反馈

按风险说明：

- 哪些输出自动发布，哪些需要人工审核。
- 风险分类、审核队列和升级规则。
- 用户纠错、举报和负反馈怎样进入后台。
- 错误样本如何标记、归因和进入改进流程。
- 是否允许重新生成、人工改写、隐藏或下架。
- 模型、提示词、知识来源和输出版本怎样追溯。
- 高风险场景的人工作业时限和兜底。

## 用户、会员与权益管理

只定义当前产品实际需要的管理能力，避免发展成通用CRM。

### 用户和会员

按需包含：

- 用户标识、账号状态、注册来源和会员状态。
- 只读信息与允许人工修改的信息。
- 标签、分群和分群来源。
- 禁用、解禁、注销和数据删除。
- 会员开通、续费、到期、暂停和恢复。
- 人工调整会员状态的权限、原因和审计。
- 用户投诉、申诉和人工处理记录。

避免允许后台随意修改由交易、订阅或外部系统维护的权威数据。

### 权益

定义：

- 权益类型、适用对象和使用场景。
- 发放条件、数量、有效期和使用限制。
- 领取、发放、冻结、使用、退回、作废和过期状态。
- 人工补发、扣回和延期的权限与原因。
- 重复发放、并发领取和库存不足。
- 权益与会员、活动、任务或订单的关系。
- 用户端展示、通知和异常补偿。
- 权益流水、操作日志和对账。

## 活动、任务与奖励配置

### 活动

定义：

- 活动目的、参与对象、入口和渠道。
- 开始、结束、报名和结果时间。
- 参与条件、次数、名额和资格判断。
- 活动内容、页面素材和用户协议。
- 奖励、权益和发放规则。
- 草稿、审核、预热、生效、暂停、结束和归档状态。
- 修改进行中活动对已参与用户的影响。
- 名额用尽、活动暂停、奖励不足和异常终止。
- 数据看板、名单导出和运营处理。

### 任务

定义：

- 任务类型、目标行为和完成判定。
- 周期、次数、累计和重置规则。
- 前置任务、任务组和互斥关系。
- 进度更新、补记、撤销和过期。
- 防刷、防重复和异常数据处理。
- 任务完成后的奖励和通知。
- 人工修正进度的权限和日志。

### 奖励

明确奖励来源、发放时机、失败重试、补发、撤销、过期、库存或预算限制，以及前台展示和用户申诉处理。

## 规则、策略与系统配置

配置功能的核心不是“可编辑”，而是安全地改变系统行为。

每条规则或配置说明：

| 维度 | 内容 |
|---|---|
| 配置对象 | |
| 业务目的 | |
| 操作角色 | |
| 适用范围 | 产品/端/版本/渠道/地区/人群 |
| 生效条件 | |
| 优先级 | |
| 冲突与互斥 | |
| 默认与兜底 | |
| 有效期 | |
| 审核与发布 | |
| 版本与回滚 | |
| 监控与验收 | |

额外检查：

- 无配置、配置缺失和配置错误时系统怎样运行。
- 多条规则同时命中时如何排序。
- 新规则是否影响已进入流程的用户。
- 开始、结束和跨时区边界。
- 配置值的格式、范围、依赖和联动校验。
- 是否支持预览、沙箱、灰度和紧急关闭。
- 修改后是立即生效、定时生效还是随版本发布。
- 历史版本是否可查看、比较、复制和恢复。

系统字典、枚举和基础配置需要明确谁能维护、哪些地方使用以及删除或改名的影响。

## 审核、发布与版本管理

### 审核流程

根据风险决定是否需要审核，不为低风险配置增加无价值流程。

明确：

- 哪些操作需要审核。
- 提交人、审核人和最终发布人。
- 是否允许自审。
- 审核通过、拒绝、撤回和重新提交。
- 审核意见是否必填和谁可见。
- 审核期间能否编辑，编辑后是否重新审核。
- 多级审核、会签和超时处理。
- 审核人无权限、离职或长时间未处理时如何转交。

### 发布

定义：

- 发布对象和版本。
- 立即、定时、灰度或分批发布。
- 发布前校验、预览和影响范围确认。
- 发布中、成功、部分成功和失败状态。
- 发布结果、失败原因和重试。
- 发布后的前台验证和监控。
- 紧急暂停、下线和回滚。
- 定时任务因服务不可用错过时间后的处理。

### 版本

按需记录：

- 版本号、创建人、提交人、审核人和发布时间。
- 修改前后差异、原因和关联需求。
- 当前生效版本和历史版本。
- 复制、比较、恢复和删除规则。
- 回滚是否产生新版本。
- 版本与客户端、模型、知识库或活动的兼容关系。

## 数据看板与运营分析

后台看板围绕角色决策和行动设计，不从“展示更多图表”出发。

每项指标说明：

- 指标名称和业务含义。
- 统计对象、事件和数据来源。
- 计算公式、分子、分母和排除条件。
- 时间口径、时区和更新频率。
- 数据延迟、补数和修正。
- 可用筛选和维度。
- 权限和敏感数据处理。
- 异常阈值和对应运营动作。

区分：

- 业务结果指标。
- 过程和漏斗指标。
- 内容、AI或运营质量指标。
- 系统健康和异常指标。

看板与明细数据应能相互解释。无法下钻时说明数据差异和责任来源。

## 通知、待办与协作

定义通知或待办时说明：

- 触发事件和接收角色。
- 站内、邮件、短信、企业协作工具等渠道。
- 内容、对象链接和下一步操作。
- 实时、汇总或定时发送。
- 重复合并、频率限制和免打扰。
- 已读、未读、处理和关闭状态。
- 接收人变化、权限撤销和发送失败。
- 是否包含敏感信息。

只有需要责任人采取动作的事项才进入待办。纯信息提醒与待办分开。

## 日志、审计与问题追溯

### 操作日志

对高风险和关键业务操作记录：

- 操作对象和唯一标识。
- 操作类型。
- 操作前和操作后。
- 操作人、角色和组织。
- 操作时间和来源。
- 原因、审批单和关联需求。
- 操作结果和失败原因。

按需覆盖登录、查看敏感信息、导出、授权、批量操作、审核、发布、回滚、人工调整和删除。

### 业务历史

用户可理解的业务轨迹与技术日志分开。业务历史应回答“谁在何时因为什么把对象从什么状态改成什么状态”。

明确：

- 哪些角色可查看。
- 是否允许导出。
- 历史记录保留期限。
- 是否需要搜索和筛选。
- 是否展示失败、撤回和回滚记录。
- 敏感字段修改前后如何脱敏。

### 问题定位

后台存在异步任务、AI生成、批量导入或外部依赖时，提供可追踪标识、任务状态、错误原因和人工重试入口。不要让运营只能向研发描述“某条数据不见了”。

## 异常、并发与数据一致性

至少按需覆盖：

- 无数据、数据缺失、数据失效和数据延迟。
- 重复创建、重复提交和重复发布。
- 多人同时编辑和版本冲突。
- 数据在编辑期间被删除、停用或改变状态。
- 批量操作部分成功。
- 导入、导出和发布任务超时。
- 外部服务、AI、接口和存储不可用。
- 后台保存成功但前台未生效。
- 前台已产生用户行为后配置被修改。
- 定时生效任务错过时间。
- 审核通过后内容或配置再次修改。
- 操作权限在页面停留期间被撤销。
- 浏览器关闭、登录过期和中断后恢复。

每个适用异常说明：

- 触发条件。
- 当前对象和任务状态。
- 系统是否重试、回滚或保持中间状态。
- 操作者看到的反馈。
- 是否允许再次操作。
- 前台用户是否受影响。
- 日志、告警和人工处理责任。

### 并发编辑

根据风险选择：

- 最后保存覆盖。
- 提交前比较版本并提示冲突。
- 编辑锁定及自动释放。
- 合并非冲突字段。

产品经理定义冲突时应保护的数据和用户结果，研发确认实现。

## 安全、隐私与合规

按风险明确：

- 最小权限和最小数据访问。
- 敏感字段脱敏、复制、下载和导出限制。
- 查看完整敏感信息是否需要申请、授权或二次验证。
- 用户数据的使用目的、保存期限、更正和删除。
- 内容、AI和用户反馈中的敏感信息处理。
- 外部合作方、测试环境和演示账号的数据隔离。
- 高风险操作的二次确认、审批和审计。
- 防止批量爬取、越权查询和恶意导出。
- 会话过期、账号禁用和异常登录。
- 日志中不得记录的敏感信息。

受监管或高风险业务必须由安全、隐私、法务或合规责任人确认。

## 非功能、发布与回滚

### 非功能要求

根据后台实际规模定义：

- 列表和详情响应要求。
- 大数据量筛选、分页、导出和批量任务。
- 并发运营和多人协作。
- 异步任务执行、进度和恢复。
- 可用性、降级和故障恢复。
- 浏览器、分辨率和设备兼容。
- 日志、监控、告警和可观测性。
- 无障碍或特殊操作人员需求。

没有数据基线时说明业务容忍度和测量方式，由研发共同确认数值。

### 发布准备

检查：

- 菜单、角色和权限初始化。
- 字典、配置、模板和默认数据。
- 历史数据迁移和兼容。
- 前后台发布顺序。
- 定时任务、消息和外部依赖。
- 测试、演示和生产环境隔离。
- 运营培训、操作手册和紧急联系人。
- 监控指标和上线观察窗口。

### 灰度与回滚

后台能力和后台配置分别考虑：

- 后台新功能能否按角色、组织或环境灰度。
- 配置是否支持按用户、渠道、版本或地区灰度。
- 关闭开关后前台如何运行。
- 回滚代码、配置和数据的顺序。
- 已发布内容、已发放权益或已完成任务如何处理。
- 回滚触发条件、权限和责任人。

## 验收标准

后台验收不仅验证页面显示，还要验证权限、数据、状态和前台影响。

每项核心需求至少覆盖：

- 正确角色在正确数据范围内完成任务。
- 无权限角色无法通过页面或其他入口越权。
- 新增、编辑、删除、停用和恢复的业务结果。
- 状态转换、审核、发布、拒绝、撤回和回滚。
- 表单必填、格式、范围、枚举和关联校验。
- 搜索、筛选、排序、分页和空结果。
- 批量操作全部成功、全部失败和部分成功。
- 导入模板、校验、错误报告、重复数据和重新导入。
- 导出范围、字段、脱敏、大数据量和下载权限。
- 多人编辑、重复提交、登录过期和权限变化。
- 前台生效范围、时间、版本和降级。
- 操作日志、业务历史、监控和告警。

建议使用：

```markdown
### AC-XXX｜验收场景
- 关联需求：
- 前置条件：
- 操作角色：
- 数据范围：
- 操作：
- 预期后台结果：
- 预期前台结果：
- 预期数据与状态：
- 预期日志/通知：
```

## PRD推荐结构

管理后台完整PRD可按需使用：

1. 文档信息与变更记录
2. 背景、目标和成功信号
3. 服务的前台产品与后台责任边界
4. 使用角色、组织和任务
5. 范围、非范围与优先级
6. 业务对象、对象关系和生命周期
7. 业务流程、状态与审批流程
8. 角色权限和数据权限矩阵
9. 信息架构、菜单和工作入口
10. 模块与页面需求
11. 列表、详情、表单和通用操作
12. 内容、AI、用户、权益、活动或规则专项要求
13. 字段、枚举、校验和数据口径
14. 批量操作、导入与导出
15. 通知、待办、日志和审计
16. 异常、并发、恢复和前台降级
17. 安全、隐私和合规
18. 非功能、监控和告警
19. 发布、迁移、灰度和回滚
20. 验收标准、依赖、风险和待确认项

不需要在每份文档中机械生成全部章节。模块少、角色少且风险低时使用轻量结构。

## 常见问题

### 先画页面，再补规则

问题：形成大量列表和表单，但角色、对象、状态和业务结果不清晰。

处理：先定义业务对象、任务、状态、权限和前台影响，再确定页面。

### 用“增删改查”代替需求

问题：没有说明什么角色在什么条件下操作，以及操作怎样影响业务。

处理：分别定义入口、前置、校验、状态、反馈、失败和后续动作。

### 所有管理员拥有全部权限

问题：增加误操作、数据泄露和责任不可追踪风险。

处理：区分菜单、操作、数据和字段权限，并按职责最小授权。

### 配置保存后立即生效

问题：缺少预览、审核、灰度、版本和回滚，错误直接影响用户。

处理：根据风险设计草稿、测试、审核、发布、生效和回滚流程。

### 导入导出只有按钮描述

问题：缺少范围、字段、校验、部分成功、敏感信息和大数据量处理。

处理：将导入导出作为独立业务流程定义。

### 只写后台结果，不写前台影响

问题：无法判断配置是否真正生效，也无法设计降级和验收。

处理：每项关键后台操作同时说明前台范围、生效时间、用户结果和失败兜底。

### 只记录技术日志

问题：运营无法理解谁修改了什么，也无法追责和恢复。

处理：同时定义面向业务人员的操作历史、版本记录和审核发布记录。

### 将案例规则直接复制到当前项目

问题：历史案例的角色、状态、字段和业务约束被误当作当前事实。

处理：案例只用于识别结构和风险，所有业务规则必须由当前项目材料或责任人确认。
