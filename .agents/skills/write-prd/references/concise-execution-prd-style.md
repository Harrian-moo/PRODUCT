# 精简执行型PRD输出规范

本规范用于统一“产品开发”目录下完整PRD和轻量PRD的默认成稿形式。它是通用的写作架构、表达语法和内容侧重，不是必须逐项填满的固定模板，也不携带任何具体产品事实。

## 0. 风格目标

生成内容应在以下三个层面接近参考型执行PRD：

### 架构

- 先让开发明确本期边界，再依次理解角色、页面、规则、流程、数据、异常和验收。
- 按用户任务、使用端或业务对象组织内容，不按产品方法论或写作者分析过程组织内容。
- 从宏观范围逐步进入实现细节，最后以依赖和上线前置收口。
- 章节名称和数量服从实际需求；允许合并、拆分或省略，但阅读顺序不应逆转。

### 表达方式

- 使用简洁的业务陈述，不使用咨询报告式长篇分析。
- 每条需求直接说明“谁在什么场景执行什么操作，系统产生什么结果”。
- 使用短标题、短段落、项目符号和窄表格形成稳定节奏。
- 不展示模型思考、评审方法、材料搜集过程或模板填充痕迹。
- 专业性来自规则无歧义和结果可验收，而不是章节数量、术语数量或技术细节数量。

### 内容侧重

- 优先写会影响开发理解和测试结果的内容：范围、权限、时间、次数、唯一性、统计、历史影响、字段校验、状态、异常和验收。
- 对背景、目标、市场、方法论、埋点、技术实现和过程记录实行“必要才写”。
- 对页面视觉只描述业务所需的结构和交互，不替代原型或视觉设计。
- 对技术只规定业务结果、依赖和验收，不替代架构、接口或数据库设计。

## 1. 默认成稿形态

除非用户明确要求其他模板，PRD直接从功能范围开始，不在正文前堆叠方法论、输入依据或评审过程。

```markdown
# 产品功能需求文档（PRD）——产品/模块名称 Vx.x

| 项目 | 内容 |
|---|---|
| 文档版本 | Vx.x |
| 修订日期 | YYYY-MM-DD |
| 文档状态 | 文字评审稿/待评审/已确认 |
| 产品经理 | 待填写/姓名 |

## 1. 功能范围
### 1.1 本次开发内容（In Scope）
#### 用户端/角色端
#### 管理端/配置端（适用时）
### 1.2 本次不开发内容（Out of Scope）

## 2. 角色权限
### 2.1 角色定义
### 2.2 权限矩阵
### 2.3 权限来源、数据范围或隐私规则（适用时）

## 3. 页面与交互说明
### 3.1 用户端
### 3.2 管理端（适用时）

## 4. 关键业务规则

## 5. 核心流程

## 6. 字段与状态
### 6.1 主要字段
### 6.2 状态流转

## 7. 异常与边界处理

## 8. 核心验收标准

## 9. 依赖与上线前置
```

以上结构是默认阅读顺序，不是固定内容清单。章节可按产品类型和需求复杂度调整；没有真实内容的章节直接省略，不输出空表或“暂无”占位。

## 2. 章节职责

| 章节 | 只回答什么 |
|---|---|
| 功能范围 | 本期做什么、不做什么；按真实使用端或角色分组 |
| 角色权限 | 谁能看、谁能操作、数据范围、权限变化和隐私边界 |
| 页面与交互 | 页面在哪里、默认展示什么、如何触发、如何反馈；不重复业务公式 |
| 关键业务规则 | 时间、次数、唯一性、去重、排序、统计、历史影响和冲突处理 |
| 核心流程 | 从入口到结果的关键顺序，不重复字段和异常表 |
| 字段与状态 | 业务字段、来源、必填、校验及对象状态变化 |
| 异常与边界 | 触发场景、系统处理、用户反馈和最终数据结果 |
| 验收标准 | 前置与操作、可观察结果；覆盖主流程、权限、重复和关键边界 |
| 依赖与上线前置 | 身份权限、初始化数据、第三方、专业审核和上线准备 |

同一规则只在一个章节定义，其他章节仅引用或验证其结果。

## 3. 表达方式

- 先写业务结果，再写必要条件。
- 使用“必须、不得、仅、支持、成功后、失败时”等确定性语言。
- 每个项目符号只承载一条规则或一个紧密相关的结果。
- 功能内容使用短段落和项目符号；映射关系使用表格。
- 简单流程使用“入口 → 操作 → 系统处理 → 结果”的单行文字链，不为形式单独绘制流程图。
- 只有三个以上分支、角色交接或状态回路难以线性表达时才使用流程图或状态图。
- 表格优先用于角色、权限、字段、状态、异常和验收；不得把普通说明文字强行装入大表。
- 页面布局和视觉以已确认原型为准；PRD不自动嵌入或重绘原型。
- 原型与文字规则冲突时，必须写明执行优先级或列出差异，不把冲突留给研发判断。

## 4. 信息密度

默认省略下列内容：

- “文档控制”“输入依据”“决策分级”等过程性章节。
- 本地路径、对话记录、Skill调用说明和写作方法。
- 大段背景、行业分析、价值口号和重复的产品定位。
- 与正文重复的FR/BR/EX追溯矩阵。
- 数据库表结构、框架、缓存、队列、锁和部署方案。
- 完整埋点字典、接口字段表、测试用例集和技术回滚步骤。
- 未经用户要求的FAQ、版本历史、决策日志和附录。

以下内容不能因精简而删除：

- In Scope与Out of Scope。
- 角色、操作权限和数据范围。
- 关键时间、次数、唯一性、统计与历史影响规则。
- 字段必填与校验。
- 状态、取消、撤销、下架和删除语义。
- 空数据、失败、重复、并发和权限异常。
- 可观察的核心验收标准。
- 会阻塞开发或上线的依赖与待确认项。

## 5. 背景、目标与指标的处理

- 背景和目标已经由上游方案或项目资料确认，且不影响本期实施理解时，不在执行稿中重复展开。
- 背景、目标或成功指标仍会影响范围和取舍时，在功能范围前增加一个简短章节，原则上只保留必要结论。
- 没有可靠基线时，不为完整性虚构目标值。
- 价值验证、埋点和效果指标需要独立展开时，放入专项文档或在正文末增加精简章节。

## 6. 页面原型的处理

- 用户已提供原型时，PRD只说明原型承担的范围以及文字规则承担的范围。
- 用户要求不展示原型图时，不嵌入截图、路径和重绘图。
- 原型缺少的新功能必须用文字说明入口、状态、反馈和空态；视觉细节由设计交付承接。
- 原型存在旧逻辑、模拟数据或与PRD不同的字段时，增加简短的“原型差异说明”，明确删除、保留和修改项。

## 7. 待确认项

- 仅保留会改变范围、对象、流程、权限、数据、验收或上线安全的待确认项。
- 能由现有资料唯一推导的规则直接关闭，不把研发常规技术选择写成产品TBD。
- 待确认项不应散落在正文中伪装为执行规则；集中放在依赖章节，标明影响阶段和责任角色。
- 存在阻塞开发的待确认项时，文档状态必须保持“文字评审稿”或“待评审”。

## 8. 输出前检查

1. 读者能否按“范围 → 权限 → 页面 → 规则 → 流程 → 字段状态 → 异常 → 验收 → 依赖”顺序完成阅读。
2. 是否在三分钟内看清本期做什么、谁能操作和最重要的三至五条规则。
3. 是否存在同一概念在多个章节重复定义。
4. 是否存在原型、正文、状态和验收互相冲突。
5. 是否可以由开发形成数据对象和接口方案，由测试形成核心测试场景。
6. 删除所有过程性内容后，文档是否仍然完整可执行。
