# 产品类型与交付环境校准

本规范供 `write-prd` 在开始成熟度检查前读取。它用于决定PRD应重点展开哪些关系、流程、规则和验收要求，不用于给产品贴固定标签，也不替代当前项目事实。

## 校准原则

- 使用“主要类型 + 次要特征 + 交付环境”描述产品，允许多种特征并存。
- 根据真实服务关系、组织边界和使用方式判断，不只根据PC端、移动端、页面样式或行业名称判断。
- ToB、ToC、内部系统、管理后台、平台工具和商业模式不是同一维度，不互相替代。
- 管理后台不等于ToB产品；ToC产品也可能包含运营后台、审核后台和配置后台。
- ToB不意味着忽略体验。体验会影响任务效率、错误率、培训成本、采用率和服务成本。
- 产品类型只决定文档关注重点，不自动决定必须使用轻量PRD或完整PRD。
- 未经确认的客户承诺、部署形式、服务等级、定制范围和性能指标必须标记为假设或待确认项。

## 最小校准记录

开始写PRD前，形成以下记录：

```markdown
### 产品类型与交付环境校准

- 主要类型：
- 次要特征：
- 服务对象与核心任务：
- 需求提出者 / 购买或决策者 / 管理者 / 实际使用者 / 受影响者：
- 组织、账号与数据边界：
- 交付和发布方式：
- 关联或依赖系统：
- 需要重点展开的章节：
- 可以降低深度或不适用的部分：
- 判断依据：
- 假设与待确认项：
```

没有足够信息时，至少确认会改变范围、流程、权限、数据或验收的项目。校准结果只影响局部章节时，明确假设后继续；可能改变产品定位或核心方案时，返回上游工作流。

## 按产品类型调整重点

### 面向个人用户的消费型产品

重点检查：

- 用户动机、触发场景、任务连续性和认知成本。
- 首次使用、授权、注册登录、跨端和中断恢复。
- 页面状态、操作反馈、容错、弱网和设备兼容。
- 个人数据的知情、授权、更正、删除和保留。
- 获客、激活、转化、使用、留存或价值达成信号。
- 内容、推荐、AI或自动化结果的解释、反馈和人工兜底。
- 消费端功能是否依赖运营、审核、客服或配置后台。

不要因为用户量大就制造统一用户画像；按真实场景区分用户分层和行为差异。

### 面向组织或客户的产品

重点检查：

- 客户、购买者、决策者、管理员、业务负责人和实际使用者是否为不同角色。
- 需求来自客户问题、岗位任务、销售反馈、实施障碍、客服问题还是合同承诺。
- 组织层级、租户、部门、岗位、账号生命周期和数据范围。
- 角色权限、审批授权、职责分离、日志审计和责任追溯。
- 端到端业务流程、跨岗位交接、异常处理和人工介入。
- 标准能力、可配置能力、客户特定需求和明确不支持范围。
- 第三方、历史系统、数据迁移、接口集成和版本兼容。
- 试点、实施、初始化、培训、验收、推广、支持和退出安排。
- 可用性、服务连续性、安全合规及适用的服务等级约束。
- 业务效率、任务完成率、错误率、覆盖率和客户结果等价值信号。

不得把单个客户提出的功能直接等同于目标市场的通用需求。记录需求来源、证据、适用客户范围、标准化价值和维护成本。

### 面向内部岗位的工作系统

重点检查：

- 使用角色的岗位职责、任务频率、工作量和当前处理方式。
- 现有制度、审批链、例外处理、线下补充流程和责任边界。
- 组织、岗位、数据权限、交接、离职和代理操作。
- 数据来源、维护责任、日志审计和问题追溯。
- 批量处理、快捷操作、导入导出和高频任务效率。
- 推广范围、账号与权限初始化、培训、切换和旧流程退出。
- 效率提升、错误减少、处理时效、流程合规和人工成本等指标。

不要只把现有线下流程原样电子化；先确认哪些步骤有业务价值，哪些只是历史习惯。

### 平台、工具或跨系统产品

重点检查：

- 服务对象、能力边界、调用方、管理方和责任系统。
- 核心对象、输入输出、状态、契约、版本和兼容策略。
- 多租户、配额、限流、权限、审计和隔离要求。
- 接入、配置、调试、错误定位、监控和退出路径。
- 稳定性、可用性、一致性、降级和生态依赖。
- 调用量、成功率、接入效率、任务完成和故障恢复等指标。

复杂接口、数据同步或独立联调验收使用 `define-interface-requirement`，不要在PRD中无限展开技术接口细节。

### 多角色、双边或前后台混合产品

重点检查：

- 分别定义每一侧用户、目标、入口、行为、结果和失败方式。
- 说明各侧之间的信息、权益、任务、内容或交易如何流动。
- 说明一侧操作如何影响另一侧，以及延迟、冲突和撤销如何处理。
- 区分消费端体验、业务端操作和运营后台配置的责任边界。
- 同时定义单侧指标和整体闭环指标，避免只优化其中一侧。

混合产品按模块加载相应要求，不把整份PRD机械写成所有类型的合集。

## 按交付环境调整重点

### 公开统一发布

- 明确平台、版本、灰度对象、兼容范围、用户通知、监控和回滚。
- 关注规模化用户影响、设备差异、应用市场或渠道约束。

### 标准化SaaS或统一云服务

- 明确租户、组织、账号、权限、配置范围、版本策略和服务连续性。
- 区分全局能力、租户配置和用户个人设置。
- 说明统一升级对不同客户、数据和集成的影响。

### 客户配置、实施或分批启用

- 区分标准产品、可配置项、实施工作和客户特定开发。
- 明确环境准备、初始化数据、权限配置、培训、试点、验收和推广责任。
- 说明配置错误、实施延期、客户未准备和回退旧流程时的处理。

### 私有环境或客户控制环境

- 先明确业务对隔离、安全、数据归属、升级窗口和运维责任的约束。
- 说明版本兼容、升级路径、数据迁移、问题诊断和支持边界。
- 未经研发确认，不在PRD中擅自指定部署架构或基础设施方案。

### 内部推广或流程切换

- 明确试点部门、账号与权限初始化、培训、并行期、强制切换和旧流程退出。
- 说明新旧数据、历史记录、未完成任务和跨部门协作如何衔接。

### 试点或灰度交付

- 明确试点对象、进入条件、观察周期、成功标准、扩大条件和停止条件。
- 区分产品假设验证、交付验收和技术稳定性验证，三者不得混为一项。

## 组织型产品的角色与需求来源

组织型或复杂内部产品按需建立角色表：

```markdown
| 角色 | 所属组织/岗位 | 目标与任务 | 决策或付费关系 | 使用频率 | 数据范围 | 主要权限 | 验收或支持责任 |
|---|---|---|---|---|---|---|---|
```

同时区分需求来源：

- 直接用户问题或行为证据。
- 客户业务目标、制度或合规要求。
- 销售、客服、实施或客户成功转述。
- 合同、招投标、服务承诺或既有交付约束。
- 内部战略、运营效率或技术治理要求。

转述内容先还原为“什么角色在什么场景遇到什么问题”，再判断是否采用对方提出的解决方案。对合同或承诺类输入记录责任人、适用客户、截止时间和变更权限。

## 章节深度映射

| 特征 | 必须重点展开 | 通常按需展开 |
|---|---|---|
| 个人消费型 | 用户场景、交互状态、隐私授权、跨端与弱网、价值指标 | 复杂权限、组织层级、实施验收 |
| 组织或客户型 | 角色链、业务流程、组织与权限、配置边界、审计、交付验收 | 消费增长漏斗、设备碎片化 |
| 内部工作系统 | 岗位任务、流程规则、权限、数据责任、推广切换 | 商业购买关系、外部客户验收 |
| 平台或跨系统 | 能力边界、系统责任、数据契约、兼容、稳定性、监控 | 高保真页面细节 |
| 多角色或混合型 | 角色关系、跨侧流程、状态影响、责任边界、闭环指标 | 与当前模块无关的其他侧细节 |
| 配置或实施交付 | 标准与定制边界、初始化、培训、试点、验收、支持 | 统一公开发布流程 |
| 私有或受控环境 | 安全隔离、数据归属、升级兼容、运维责任 | 应用市场发布要求 |

该表用于选择深度，不用于删除当前需求实际需要的章节。

## 关键问题

信息不足时，从以下问题中选择最多3至5个最影响决策的问题：

1. 谁提出需求、谁决定或付费、谁管理、谁实际使用、谁承担结果？
2. 是否存在组织、租户、岗位、审批、数据范围或跨组织协作？
3. 这是所有用户的标准能力、可配置能力，还是特定客户或部门的要求？
4. 产品如何交付、启用和验收，由谁完成初始化、培训、支持和最终确认？
5. 是否依赖历史系统、第三方、数据迁移、私有环境、安全或合规要求？

用户无法立即回答时，只把会改变范围、方案或验收的项目设为阻塞；其余项目明确假设后继续。

## 常见误区

- 不根据页面是Web端还是移动端直接判断ToB或ToC。
- 不把管理后台规范套用到所有组织型产品。
- 不因ToB业务复杂就默认生成重型PRD，文档深度仍取决于当前变更范围和风险。
- 不因ToC强调体验就省略业务规则、异常、数据、权限或发布要求。
- 不把客户、销售或领导提出的功能直接写成用户需求。
- 不把合同承诺、定制开发、标准产品和实施配置混写在同一范围中。
- 不以“交互不重要”为由省略可用性、反馈、效率和无障碍要求。
- 不替研发承诺未经确认的架构、部署方式、性能数值或服务等级。

## 完成检查

校准完成后确认：

1. 已识别主要类型、次要特征和交付环境，而非只写一个ToB或ToC标签。
2. 已区分需求提出者、决策者、管理者、使用者和受影响者。
3. 已识别组织、账号、权限、数据和系统边界。
4. 已说明标准能力、配置、定制和非范围之间的关系（适用时）。
5. 已识别发布、实施、培训、迁移、验收和支持责任（适用时）。
6. 已把类型差异转化为PRD章节深度、待确认项和验收要求。
7. 没有把参考清单当作当前项目事实，也没有为了完整而扩大范围。
