# 项目状态汇报与向上沟通

## 目标

在产品开发的每个关键节点，将当前阶段的复杂输出浓缩为不同深度、适配不同受众和时长的汇报文案。

重点回答：

- 给 30 秒电梯里的人说什么？给 3 分钟会议室的人说什么？给 5 分钟详细讨论的人说什么？
- 当前阶段最重要的一个结论是什么？
- 需要领导做什么决策？
- 最大的风险是什么，需要谁关注？
- 下一步是什么，什么时候能看到什么结果？

最终交付物为三份文案，每份独立可用，不是同一篇内容的逐级缩写。

## 工作边界

本 Skill 负责：

- 从任何已完成 skill 的输出物中提取汇报关键信息。
- 将产品语言转化为管理层易懂的业务语言。
- 按三种时长生成结构不同的汇报文案。
- 识别当前阶段最需要领导关注的风险和决策点。

本 Skill 不负责：

- 重新分析产品、修改方案或补充 PRD 内容。
- 替代正式的项目周报或 OKR 跟踪系统。
- 在没有可汇报内容时编造进展。
- 替代演示文稿（PPT）的设计——只输出文案内容。

## 基本原则

1. 三种版本不是量变是质变——结构、重点、语言深度都不同。
2. 1 分钟版只讲"结论 + 关键决策 + 最大风险"。
3. 3 分钟版补充"背景 + 方案概要 + 关键取舍 + 下一步"。
4. 5 分钟版增加"数据支撑 + 分析过程 + 依赖详情 + 备选方案"。
5. 向上汇报的核心不是"我做了什么"，而是"你需要知道什么"和"你需要做什么决策"。
6. 每个版本必须包含明确的决策请求或信息同步声明。
7. 业务语言优先，减少产品术语；必须使用的术语加一句解释。

## 工作流程

### 1. 识别当前阶段和汇报触发点

| 节点 | 触发条件 | 汇报重点 |
|------|----------|----------|
| 概念确认后 | `product-concept-discovery` 完成 | 产品机会、目标用户、差异化、是否值得继续投入 |
| 功能发散后 | `ideate-features` 完成 | 核心创意方向、创新亮点、建议优先验证的方向 |
| 规划确认后 | `plan-product` 完成 | 模块架构、MVP 范围、优先级、资源需求预估 |
| 方案确认后 | `design-feature-solution` 完成 | 推荐方案的机制、关键取舍、与替代方案的区别 |
| PRD 评审前 | `write-prd` 完成 | 本期范围、核心功能、风险项、需要的跨团队配合 |
| 审查通过后 | `review-requirement` 完成 | 审查结论、已解决问题、残留风险和上线建议 |
| 上线计划确认 | `validate-launch` 完成 | 灰度策略、回滚条件、关键监控指标、责任分工 |
| 复盘完成 | `iterate-review` 完成 | 指标达成情况、关键发现、经验教训、下一迭代建议 |

如果汇报不在标准节点（如突发问题、临时汇报），根据用户提供的上下文判断重点。

### 2. 提取关键信息

- **一个核心结论**：如果只能传达一句话，那是什么。
- **三个支撑要点**：支撑核心结论的最重要事实或分析。
- **一个决策请求**：需要领导做什么决定（没有则标注"仅同步信息"）。
- **一个最大风险**：当前阶段最需要领导关注的不确定性。
- **下一步和时间预期**：接下来做什么，大概什么时候有下一步结果。

### 3. 按三种版本输出

#### 🕐 1 分钟版（电梯演讲 / 微信消息）

**结构**：

```
【核心结论】一句话
【关键支撑】最多三点，用"•"列出
【决策请求】一句话，或"仅供参考"
【风险】一句话，最大风险
```

**约束**：全文 ≤ 150 字。不需要背景铺垫，直接说结论。不解释术语，不展开分析过程。必须有明确的决策请求或信息同步声明。

#### 🕒 3 分钟版（标准汇报 / 站会同步）

**结构**：

```
## 一句话结论
## 背景（2-3 句）
## 当前阶段与产出
## 核心方案 / 关键发现（3-5 要点）
## 关键取舍与理由
## 主要风险
## 下一步与时间预期
## 需要什么决策或支持
```

**约束**：全文约 300-500 字。背景只写必要上下文，不从头讲起。每个要点一行，不展开论证。取舍必须说"选了 A 不选 B，因为 XXX"。

#### 🕔 5 分钟版（详细汇报 / 评审会）

**结构**：

```
## 执行摘要（一段话）
## 背景与问题
## 当前阶段产出概述
## 方案 / 数据分析（可含对比表、数据支撑）
## 关键决策与取舍分析（每个决策说明"选了什么、没选什么、为什么"）
## 风险与缓解措施（分组：业务风险 / 技术风险 / 运营风险 / 合规风险）
## 资源与依赖
## 下一步计划（含时间窗口）
## 需要的决策（明确决策选项和推荐）
```

**约束**：全文约 600-1000 字。每个数据点有来源。每个风险有缓解措施。每个决策请求有明确选项和推荐。但仍是文案，不是完整 PRD——不展开字段、状态、接口细节。

## 对话与协作方式

1. 用户提供已完成 skill 的输出物（或指定阶段），Skill 自动识别节点。
2. 默认三种版本都输出。用户可指定只输出某一种。
3. 用户可指定汇报对象（直属领导 / 跨部门合作方 / 高层），调整语言风格和术语密度。
4. 用户可指定汇报形式（口头 / 邮件 / 评审会），调整结构侧重。
5. 如果当前阶段信息不足以支撑汇报，诚实指出缺失项，不编造。

## 输出要求

- 默认中文。
- 三种版本之间的差异必须肉眼可见——不是同一篇文案的剪切和粘贴。
- 1 分钟版必须可以在 60 秒内读完（或 30 秒说完）。
- 决策请求必须明确：需要谁、做什么决定、什么时候需要。
- 风险描述必须具体，不用"可能存在不确定性"这类空话。
- 不把产品文档直接压缩成汇报——管理层不需要知道字段名和校验规则。

## 质量检查

1. 三种版本是否结构不同而非长度不同。
2. 1 分钟版是否 ≤ 150 字且包含核心结论 + 决策请求。
3. 3 分钟版是否有取舍说明（选了 A 不选 B）。
4. 5 分钟版是否每个风险有缓解措施。
5. 每个版本是否有明确的决策请求或信息同步声明。
6. 是否避免了产品术语堆砌（或对必要术语做了解释）。
7. 是否避免了"进展顺利""按计划推进"等无信息量的表述。

## 与其他 Skill 衔接

- 本 Skill 不改变产品开发流程，可在任何节点被调用。
- 接受任何已完成 skill 的输出物作为输入（规划方案 / 功能方案 / PRD / 审查报告 / 上线计划 / 复盘报告）。
- 可以单独调用，不依赖前置 skill 的完整流程。
- 汇报后如产生新的决策或方向变更，回到对应 skill 修订。
