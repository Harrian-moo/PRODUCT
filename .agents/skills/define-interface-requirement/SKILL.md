# 接口与跨系统需求定义

## 目标

把已确认的业务流程拆解为系统之间可以共同理解、实施、联调、验收和追溯的业务契约。

重点回答：

- 哪些系统和参与方需要协作，各自负责什么。
- 哪一方提供数据，哪一方使用数据。
- 由谁发起，在什么业务节点触发。
- 需要实时、异步、定时还是批量处理。
- 需要传递哪些业务信息，数据从哪里产生。
- 成功、失败、重复、延迟和部分成功时怎样保持业务一致。
- 权限、安全、隐私、性能和可观测性有什么要求。
- 双方如何联调、验收、变更和承担责任。

最终交付物默认为《接口与跨系统需求说明》。简单需求可以只输出PRD中的接口章节；复杂需求输出独立文档。

## 工作边界

本Skill负责：

- 识别系统、组织和第三方之间的业务责任边界。
- 建立数据提供方、数据使用方和责任系统关系。
- 判断推送、拉取、同步、异步、定时和批量等业务要求。
- 建立接口或数据交换清单。
- 定义每个接口的业务场景、触发、输入、输出、状态和验收。
- 定义字段业务含义、来源、必填、校验和敏感级别。
- 定义超时、重试、幂等、去重、乱序、补偿、对账和人工处理要求。
- 定义认证授权、隐私、安全、限流、日志、监控和告警要求。
- 明确联调环境、测试数据、责任人、依赖、版本和变更规则。

本Skill默认不负责：

- 决定尚未确认的产品定位、功能方案或系统职责。
- 指定数据库、表结构、框架、中间件、部署和网络拓扑。
- 在缺乏研发依据时规定HTTP路径、Method、协议、序列化方式和具体错误码。
- 把直接写入其他系统数据库作为默认集成方式。
- 替研发生成完整OpenAPI、Swagger、Apifox或YApi技术定义。
- 替安全、法务或合规责任人做专业结论。
- 替测试团队穷举全部接口测试用例。

用户已经提供技术接口文档时，可将其中已确认的路径、参数和错误码作为输入引用，但不得擅自改写技术事实。

## 是否需要独立文档

满足以下任一条件时，优先输出独立《接口与跨系统需求说明》：

- 涉及两个及以上独立系统或外部组织。
- 接口较多，无法在PRD单一章节中清晰表达。
- 存在实时、异步、定时、批量、全量或增量同步。
- 存在复杂状态映射、流程衔接或历史数据处理。
- 需要处理超时、重试、重复、乱序、部分成功、补偿或对账。
- 涉及敏感数据、跨主体授权、安全、审计或合规要求。
- 双方由不同团队开发、独立发布或需要正式联调验收。
- 接口需要复用、版本管理或独立变更控制。

以下情况保留在PRD接口章节即可：

- 仅有一个简单内部调用。
- 字段少、状态简单且不影响核心流程。
- 没有独立发布、敏感数据和复杂一致性风险。
- 同一团队可在技术设计中直接承接。

不要为了形式拆分文档。判断依据是协作复杂度和风险，不是接口数量本身。

## 基本原则

1. 从业务流程和系统职责出发，不从接口地址或技术方案出发。
2. 对每条数据流明确提供方、使用方、责任系统和业务对象。
3. 把实时性、一致性和失败后果写成业务要求，由研发选择实现方式。
4. 区分已确认业务要求、技术约束、产品建议、假设和待确认项。
5. 同一业务对象、字段、状态和错误含义只定义一次。
6. 正常结果和异常结果同等重要，不只描述调用成功。
7. 跨团队文档必须由双方产品和研发共同确认。
8. 对敏感数据遵循最小必要、明确授权、可审计和可删除原则。
9. 不制造字段、状态、性能数值、第三方能力和技术实现。
10. 接口技术文档与产品需求不一致时，先确认责任人和最新基线，不自行拼接。

## 工作流程

### 1. 确认输入成熟度

开始前确认：

- 业务目标、用户场景和本期范围已经明确。
- 端到端业务流程和关键状态已经确认。
- 为什么需要跨系统协作已经成立。
- 涉及哪些系统、组织、团队和第三方可以识别。
- 主要业务对象、数据和责任系统可以识别。
- 已知的技术、安全、隐私、合规和时间约束已经提供。

若系统职责或功能机制仍在探索，先返回 `design-feature-solution`。若只是一个简单接口，在 `write-prd` 中完成，不强制进入本Skill。

### 2. 建立系统协作基线

形成：

```markdown
### 协作基线
- 所属产品/模块：
- 业务目标：
- 本期范围：
- 非本期范围：
- 涉及系统：
- 涉及组织/团队：
- 核心业务对象：
- 责任系统：
- 已确认约束：
- 相关PRD/流程/技术文档：
- 假设和待确认项：
```

系统达到三个及以上或存在循环、异步和多阶段状态时，使用系统关系图或数据流图表达整体关系。

### 3. 识别数据提供与使用关系

对每条数据流分别确认：

- 数据或能力由哪个系统产生和维护。
- 哪个系统是权威来源。
- 哪些系统只读取、缓存、加工或展示。
- 谁对数据正确性、时效和修复负责。
- 数据变化由哪一方最先知道。
- 数据失败或延迟会影响哪个业务步骤。

不要把“发起请求的一方”自动等同于“数据使用方”，也不要把“接收请求的一方”自动等同于“数据提供方”。

### 4. 分类系统协作场景

按业务主动性和数据角色识别四类场景：

1. **我方主动推送**：我方产生或维护数据，主动发送给对方。
2. **对方主动获取**：我方提供数据或能力，对方按需调用。
3. **我方被动接收**：对方产生数据，在业务节点主动推送给我方。
4. **我方主动获取**：我方在业务节点或计划任务中向对方获取数据。

同一业务流程可能包含多个场景，应分别编号。分类用于澄清责任和触发关系，不用于指定技术实现。

### 5. 定义时效和同步语义

根据业务结果说明：

- 用户操作是否必须等待结果。
- 允许的业务延迟和超时后果。
- 实时、准实时、异步、定时或人工触发。
- 全量、增量或按条件查询。
- 新增、修改、删除和撤回如何传播。
- 数据顺序是否重要，迟到数据如何处理。
- 是否允许最终一致，何时必须强一致。
- 数据多久未同步需要告警或人工介入。

不要直接把MQ、HTTP、数据库同步或某种中间件写成产品结论。若业务具有不可替代的技术限制，标明来源并由研发确认。

### 6. 建立接口与数据交换清单

每项至少包含：

| 字段 | 说明 |
|---|---|
| 接口编号 | 使用稳定编号，如 IF-001 |
| 业务名称 | 使用业务语言描述 |
| 场景类型 | 推送、获取、接收或被获取 |
| 提供方/使用方 | 系统和责任团队 |
| 触发节点 | 对应业务流程节点 |
| 时效 | 实时、异步、定时或批量 |
| 业务对象 | 订单、用户、活动等 |
| 关键结果 | 成功后推进的业务状态 |
| 依赖与风险 | 上游、下游和主要风险 |
| 责任人/状态 | 草案、待确认、已确认 |

清单先于详细字段。接口边界未稳定时，不要急于填写参数表。

### 7. 定义单接口业务契约

对每项接口说明：

- 业务目的和使用场景。
- 提供方、使用方和责任系统。
- 发起方、触发事件和前置条件。
- 请求或推送的业务对象。
- 需要传递的业务输入。
- 返回、确认或回执的业务结果。
- 成功后的状态和数据变化。
- 失败后的状态、用户反馈和下一步。
- 重复调用、延迟到达和并发时的业务结果。
- 适用权限、安全、性能和验收要求。

详细结构使用 [接口需求模板](references/interface-requirement-template.md)。

### 8. 定义字段与状态契约

业务字段至少确认：

- 业务名称和含义。
- 所属业务对象。
- 提供方及取值来源。
- 是否必填和适用条件。
- 业务格式、枚举、范围和默认值。
- 空值、未知值和历史值处理。
- 敏感级别、展示和日志脱敏要求。
- 新增、修改、删除和版本兼容影响。

产品经理使用业务字段名，不替研发编造数据库字段名。技术字段由研发在接口技术文档中映射。

存在跨系统状态时，建立状态映射表，明确：

- 两边状态是否一一对应。
- 哪个事件触发状态变化。
- 未知、失效、回退和终态怎样处理。
- 两边状态不一致时以谁为准。
- 状态更正如何传播和审计。

### 9. 定义异常与一致性要求

至少检查：

- 请求超时、网络中断和服务不可用。
- 自动重试条件、次数原则和停止条件。
- 幂等键、业务唯一标识和重复数据处理。
- 重复请求、重复通知和重复回执。
- 消息乱序、迟到、丢失和重复消费。
- 部分成功和批量失败。
- 数据写入成功但回执或通知失败。
- 状态更新成功但下游处理失败。
- 补偿、回放、对账、修复和人工处理。
- 上游撤回、更正、删除和历史重放。
- 降级、暂停、恢复和业务连续性。

对每个适用异常说明触发条件、各系统状态、用户或运营反馈、恢复方式和责任方。

### 10. 定义安全、隐私和非功能要求

按风险说明：

- 调用身份、用户授权和系统权限。
- 数据最小化、用途、保存周期和删除要求。
- 传输、存储、展示、日志和导出中的敏感信息处理。
- 签名、防重放、访问控制和审计要求。
- 响应时限、吞吐、并发、批量上限和限流要求。
- 可用性、降级、恢复和容灾要求。
- 日志、业务流水号、链路标识、监控和告警要求。
- 第三方配额、费用、服务等级和变更风险。

缺少基线时描述业务影响和测量方式，由研发给出可行值，不制造精确数字。

### 11. 定义联调、验收和发布

明确：

- 双方产品、研发、测试、数据和安全责任人。
- 联调环境、访问条件、测试账号和测试数据责任。
- 正常、异常、边界、重复、超时和权限验收场景。
- 双方状态、数据和日志的核对方式。
- 上线顺序、前置配置、开关、灰度和回滚。
- 历史数据初始化、迁移、补数和校验。
- 监控、告警、值守、问题升级和人工兜底。
- 验收证据和最终确认责任。

只有双方对同一版本和同一验收标准达成一致，才建议进入联调。

### 12. 管理版本和变更

对接口需求变更记录：

- 修改前和修改后。
- 变更原因和提出方。
- 受影响的接口、字段、状态、系统和历史数据。
- 是否向后兼容。
- 双方开发、测试、发布和回滚影响。
- 技术接口文档是否同步更新。
- 责任人、确认日期和生效版本。

新增或删除字段不能只改参数表，必须检查业务流程、数据存量、验收和下游使用影响。

### 13. 形成交付和待确认清单

输出前将内容分为：

- 已确认业务契约。
- 研发需要设计的技术事项。
- 双方产品需要决策的业务事项。
- 数据、安全、隐私或合规需要审核的事项。
- 阻塞联调或发布的依赖。

不要把未确认内容伪装成最终接口要求。

## 《接口与跨系统需求说明》结构

根据复杂度选择必要章节：

1. 文档信息和变更记录
2. 背景、目标、范围与非范围
3. 系统、组织和责任边界
4. 业务流程、系统关系和数据流
5. 业务对象、权威数据源和状态模型
6. 接口与数据交换清单
7. 单接口业务契约
8. 字段、枚举和状态映射
9. 时效、全量/增量和同步规则
10. 异常、一致性、补偿和对账
11. 权限、安全、隐私和审计
12. 性能、限流、可用性和可观测性
13. 联调、测试和验收
14. 发布、迁移、灰度和回滚
15. 依赖、风险、责任人与待确认项
16. 技术接口文档交接清单

## 输出要求

- 默认使用中文，先给系统关系和接口清单，再展开单接口细节。
- 使用业务语言定义需求，技术术语保留时说明业务含义。
- 每个接口可追溯到业务流程节点、功能需求和验收场景。
- 每个字段说明来源、含义、校验和责任系统。
- 每个失败场景说明双方状态、恢复方式和责任方。
- 明确产品需求与研发技术设计的分界。
- 未确认的地址、参数、错误码和性能值标记责任人，不自行补齐。
- 不把参考案例、历史接口或其他产品规则当作当前事实。

## 质量检查

输出前确认：

1. 是否说明为什么需要跨系统协作。
2. 是否明确系统、组织、团队和责任边界。
3. 是否明确数据提供方、使用方和权威来源。
4. 是否明确发起方、触发节点和前置条件。
5. 是否明确实时性、全量/增量和新增/修改/删除规则。
6. 接口清单是否覆盖完整业务流程。
7. 单接口是否有输入、输出、状态和业务验收。
8. 字段、枚举和状态映射是否一致。
9. 是否覆盖超时、重试、幂等、重复、乱序和部分成功。
10. 是否定义补偿、对账、修复和人工处理。
11. 是否按风险覆盖权限、安全、隐私和审计。
12. 是否定义性能、限流、可用性、日志、监控和告警。
13. 是否明确联调环境、测试数据、责任人和验收证据。
14. 是否检查版本兼容、历史数据、发布顺序和回滚。
15. 是否区分产品业务契约和研发技术接口文档。
16. 是否标记假设、冲突、依赖和待确认项。

## 与其他Skill衔接

- 产品定位、用户问题或价值主张不清晰时，使用 `product-concept-discovery`。
- 产品架构、模块边界、MVP或版本范围不清晰时，使用 `plan-product`。
- 功能机制、端到端流程或系统协作方式不清晰时，使用 `design-feature-solution`。
- 简单接口保留在 `write-prd`；复杂接口由 `write-prd` 路由到本Skill形成独立说明。
- 需要审查已有接口需求的完整性、一致性和风险时，使用 `review-requirement` 的接口专项审查。
- 本Skill完成后，由研发生成或更新正式技术接口文档，并由双方共同联调验收。

本Skill负责定义跨系统业务契约，不替代产品方案决策、研发技术设计、正式安全审核或测试执行。
