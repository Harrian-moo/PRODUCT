# PRD 输出后复核编排

## 目标

在 PRD 新建或重大修订后，通过统一入口调用 `review-requirement`，判断文档是否可以进入后续评审、设计、研发或测试，并把发现的问题路由回正确的处理环节。

本 Skill 只负责编排复核，不复制 `review-requirement` 的检查维度、严重度规则和完整报告模板。

## 触发条件

满足以下任一条件时使用：

- 用户明确要求在 PRD 输出或修改后继续复核。
- 当前项目的工作协议明确规定 PRD 完成后必须经过质量闸门。
- 用户要求对一次重大修订执行回归式需求审查。

仅完成小范围措辞调整、格式修改或用户只要求写作而未要求复核时，不自动扩大任务范围；可提示下一步可使用 `review-requirement`。

## 工作流程

### 1. 确认复核对象

记录：

- PRD 文件或对话交付物。
- 文档版本、状态和更新时间。
- 本次是新建、完整改版还是局部修订。
- 修订章节及可能受影响的流程、规则、数据、接口、设计和验收项。
- 当前项目明确规定的专项质量要求（如有）。

### 2. 选择审查模式

| 场景 | 调用 `review-requirement` 的模式 |
|---|---|
| 全新PRD、核心流程或范围发生重大变化 | 完整需求审查 |
| 局部功能、规则、字段或流程修订 | 变更影响审查 |
| 评审前快速筛查或时间受限 | 快速准入检查 |
| 跨系统、接口、一致性或安全风险突出 | 在对应模式上增加接口专项审查 |

模式选择依据风险和变更影响，不以对话长短决定。

### 3. 加载项目专项要求

先读取当前项目已确认的产品原则、术语、模块边界、权限模型、设计规范和合规要求。只有这些材料明确要求时，才增加后台、接口、创新、游戏化、品牌或行业专项检查。

不得把其他项目的角色体系、模块名称、积分机制、终端规范或行业规则带入当前审查。

### 4. 执行并汇总

由 `review-requirement` 输出问题证据、影响、严重度、责任角色和修改建议。本 Skill 只汇总：

- 审查对象与模式。
- 准入结论：通过、条件通过或需修订。
- 各严重度问题数量。
- 最高优先级的 1—3 个问题。
- 需要返回的环节和建议动作。

### 5. 路由后续动作

- 文档表达、执行细节或验收缺失：返回 `write-prd` 修订。
- 系统边界、接口契约或一致性问题：返回 `define-interface-requirement`。
- 核心功能机制未决：返回 `design-feature-solution`。
- 产品定位、范围或MVP发生根本冲突：分别返回 `product-concept-discovery` 或 `plan-product`。
- 只有在用户授权修订时才直接修改原文；仅要求审查时只报告问题。

## 默认输出

```markdown
## PRD 复核结果
- 审查对象：
- 审查模式：完整 / 快速 / 变更影响 / 接口专项
- 结论：通过 / 条件通过 / 需修订
- 问题统计：S0 __｜S1 __｜S2 __｜S3 __
- 最高优先级问题：
  1. 
- 建议返回环节：
- 下一步：
```

默认先展示结论和最高优先级问题；用户明确要求时再展开完整审查报告。

## 质量检查

1. 是否有明确触发依据，而不是对所有写作任务强制追加工作。
2. 是否根据新建或变更范围选择了正确模式。
3. 是否实际调用 `review-requirement`，而非在本 Skill 内重复审查清单。
4. 专项要求是否来自当前项目的已确认资料。
5. 结论是否与问题严重度和准入规则一致。
6. 是否把问题路由到正确的上游或文档环节。
