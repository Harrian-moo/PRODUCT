# 迭代复盘与下一迭代建议

## 目标

在上线后观察期结束后，基于可观察的行为和数据，系统性地回答"这次做对了吗、学到了什么、下一步做什么"。

重点回答：

- 目标指标是否达成？与预期差距的原因是什么？
- 用户实际行为和数据中有哪些意外发现？
- 用户反馈中反复出现的主题是什么？
- 本次迭代最大的经验教训是什么？
- 下一迭代的优先级和范围建议是什么？

最终交付物为《迭代复盘报告》。它不是研发层面的技术回顾（那是 Sprint Retro），也不是运营层面的用户反馈汇总，而是产品层面的"下一步决策依据"。

## 工作边界

本 Skill 负责：

- 对比上线前设定的目标指标与实际数据。
- 分析用户行为漏斗、分群差异和意外发现。
- 分类整理用户反馈（定量 + 定性），提取主题。
- 进行根因分析——表面的问题是"什么"，背后的原因是"为什么"。
- 提取可复用的经验教训。
- 形成下一迭代的优先级建议（做什么、不做什么、为什么）。
- 判断是否需要调整产品策略或方向。

本 Skill 不负责：

- 在没有数据和反馈的情况下进行推测性复盘。
- 替代研发团队的 Sprint Retro 或技术复盘。
- 编写新迭代的 PRD（那是 `write-prd` 的事）。
- 替代用户研究团队的完整分析。
- 在没有权限时解读敏感业务数据。

## 基本原则

1. 复盘以数据和事实驱动，不靠印象和感觉。
2. 指标未达成不一定是失败——关键是理解为什么，以及是否可操作。
3. 对意外发现保持开放——最有价值的洞察往往不在计划之内。
4. 区分"用户不会用"和"用户不需要"——前者是交互问题，后者是价值问题。
5. 每个教训必须可转化为下一迭代的具体行动，不能停留在"下次注意"。
6. 诚实面对失败信号——该调整方向时不要用"再多做一版看看"拖延。

## 工作流程

### 1. 确认复盘基线

从 PRD 和上线计划中提取：

- **本迭代目标**：当初设定的用户结果和业务结果。
- **成功指标**：PRD 中定义的指标、口径、预期值。
- **上线时间与观察周期**：全量上线时间、数据观察窗口。
- **版本范围**：本迭代包含的功能清单。
- **关键假设**：上线前未经验证的核心假设。

### 2. 数据回顾

#### 2.1 指标对比

| 指标 | 预期值 | 实际值 | 达成率 | 差距分析 |
|------|--------|--------|:---:|------|
| | | | | |

对未达成的指标追问：是目标定高了、执行不到位、还是假设本身有问题？

#### 2.2 用户行为分析

- **漏斗分析**：关键路径的每一步转化率。最大流失点在哪个步骤？
- **使用深度**：用户是否只用了表层功能？有多少人用到了核心价值？
- **留存与复用**：首次使用后多少用户再次使用？复用频率与预期一致吗？
- **分群差异**：不同角色/层级/机构的用户行为是否有显著差异？

#### 2.3 意外发现

- 有没有用户以一种完全没预料到的方式使用产品？
- 有没有某个功能的使用量远超或远低于预期？
- 数据中是否有之前未被识别的用户群体或场景？

### 3. 用户反馈归类

#### 3.1 反馈来源

- 应用内反馈 / 评价
- 客服工单 / 投诉
- 用户访谈 / 问卷
- 内部试用反馈
- 社交媒体 / 社区讨论

#### 3.2 分类与主题提取

| 类型 | 说明 | 示例 |
|------|------|------|
| 功能缺失 | 用户需要但目前没有的能力 | "希望能导出数据" |
| 体验问题 | 能完成但不好用、不流畅 | "每次都要点三次才能到" |
| Bug 与错误 | 系统行为与预期不符 | "提交后页面卡住了" |
| 理解障碍 | 用户不知道功能存在或不知道怎么用 | "原来还有这个功能" |
| 方向性质疑 | 用户认为这个产品方向本身有问题 | "我觉得这个没什么用" |

对反复出现（≥ 3 次）的同类反馈单独标注为"高优先级信号"。

### 4. 问题与根因分析

对 Top 3-5 个问题（按影响面 × 严重度排序），追问根因：

```
表面现象 → 直接原因 → 根因 → 可操作的改变
```

区分：
- **设计问题**：交互、文案、信息架构 → 可快速迭代。
- **功能问题**：缺少必要功能 → 需要新版本。
- **价值问题**：方向本身不受欢迎 → 需要重新审视定位，不可用迭代掩盖。

### 5. 经验与教训

| 编号 | 经验/教训 | 证据 | 可操作行动 | 影响范围 |
|:--:|------|------|------|------|
| L-01 | 下期 PRD 应增加 X | 测试遗漏了 3 个异常场景 | | 研发流程 |

教训必须具体、可操作。不接受"沟通不够""测试不充分"等无法转化为行动的空泛教训。

### 6. 下一迭代建议

#### 6.1 优先级建议

| 优先级 | 项目 | 类型 | 依据 | 建议迭代 |
|:--:|------|------|------|:--:|
| P0 | | 修复/优化/新增/下线 | 数据/反馈/根因 | |

#### 6.2 范围建议

- **建议本期做**：有明确数据/反馈支撑，影响核心指标。
- **建议暂缓**：有需求信号但证据不足或依赖未满足。
- **建议不做**：反馈量小、与核心方向偏离或可通过其他方式解决。
- **建议下线**：使用率极低且维护成本高的功能。

#### 6.3 策略调整建议

如果数据或反馈表明产品方向需要调整，明确提出：

- 当前方向的问题是什么。
- 建议调整到哪个方向。
- 调整需要哪些前置验证。

策略调整是重大决策，不以单次迭代的数据做唯一依据。

### 7. 输出复盘报告

形成《迭代复盘报告》。根据实际情况选择必要章节，不为填满模板而编造分析。

## 输出结构

### 《迭代复盘报告》

1. **复盘基线**：版本号、上线时间、观察周期、本迭代目标与指标。
2. **指标达成**：每个指标的预期 vs 实际、达成率、差距分析。
3. **用户行为洞察**：漏斗、深度、留存、分群差异、意外发现。
4. **用户反馈汇总**：按来源和类型分类、高优先级信号标注。
5. **关键问题与根因**：Top 3-5 个问题的根因链和可操作建议。
6. **经验教训**：可复用的具体教训，附证据和行动。
7. **下一迭代建议**：优先级、范围建议、策略调整建议（如适用）。
8. **待验证假设**：本次复盘提出的新假设，建议验证方式。

## 对话与协作方式

1. 先确认复盘基线和可用数据来源。
2. 每轮聚焦一个维度（指标 → 行为 → 反馈 → 根因 → 建议），不一次性展开所有分析。
3. 数据不足时，明确标注"数据不足，以下分析基于有限样本"。
4. 对策略调整建议保持谨慎——单次迭代的复盘不轻易动摇产品方向。
5. 用户只要求某个维度（如只看数据、只看反馈）时，只输出那部分。

## 输出要求

- 默认中文，以数据和证据驱动。
- 指标对比用实际数字，不写"显著提升""有所下降"。
- 根因分析追问到"为什么"而非停在"是什么"。
- 每项建议必须有依据（数据/反馈/根因），不能是凭空判断。
- 不做无数据的市场推断或竞品猜测。
- 区分"证据充分的结论"和"基于有限信号的推测"。

## 质量检查

1. 是否每个目标指标都有预期值和实际值的对比。
2. 用户反馈是否按类型分类并提取了主题。
3. 关键问题是否有从现象到根因的完整链。
4. 是否有至少一条可复用的具体教训。
5. 下一迭代建议是否有明确的优先级和依据。
6. 策略调整建议是否有充分证据支撑。
7. 是否区分了"数据支持的结论"和"分析者的推测"。

## 与其他 Skill 衔接

- 上线前的目标指标来自 `write-prd`，上线策略来自 `validate-launch`。
- 数据不足时，需延长观察周期或补充用户访谈，不强行复盘。
- 复盘后的迭代建议进入 `plan-product` 开始新一轮规划，而不是直接进入 `write-prd`。
- 如果复盘发现方向性错误，回到 `product-concept-discovery` 重新审视定位。
- 本 Skill 不替代研发 Sprint Retro，不替代运营数据分析团队的深度报告。
