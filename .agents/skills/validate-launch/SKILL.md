# 上线策略与发布计划

## 目标

将已确认的 PRD 中的发布要求、依赖和风险转化为结构清晰、可执行、可应急的上线计划。

重点回答：

- 这个版本怎么上线——全量还是灰度？灰度节奏是什么？
- 如何判断上线是否顺利——观察哪些指标、看多久？
- 出了问题怎么办——回滚条件、步骤、通知谁？
- 谁在什么时间做什么——责任分工和沟通计划。
- 上线前的最后一道检查——有没有遗漏项？

最终交付物为《上线发布计划》。它不替代运维发布系统或技术部署方案，只定义业务侧的上线策略和决策条件。

## 工作边界

本 Skill 负责：

- 从 PRD 和需求审查报告中提取发布相关的范围、依赖和风险。
- 设计灰度策略（比例、观察指标、放量条件、回滚触发条件）。
- 定义功能开关（位置、默认值、紧急关闭流程）。
- 制定回滚方案（触发条件、步骤、数据回滚范围、用户通知）。
- 配置上线后监控指标和告警规则。
- 明确责任人、时间安排和沟通计划。
- 输出上线检查清单（上线前 + 上线中 + 上线后）。

本 Skill 不负责：

- 编写或修改 PRD 内容。
- 制定研发技术部署方案（容器、流水线、数据库迁移脚本）。
- 承诺研发排期或运维 SLA。
- 替代运维监控系统或告警平台的配置。
- 处理组织层面的变更管理审批（但可输出审批所需的材料摘要）。

## 基本原则

1. 灰度不是目的，可控才是目的——能用开关解决的问题不依赖回滚。
2. 回滚条件要具体、可判断，不能是"感觉有问题"。
3. 监控指标要能快速反映用户价值是否成立，而不只是系统是否存活。
4. 每个角色的职责要明确到"谁在什么情况下做什么"。
5. 上线计划在 PRD 评审通过后就必须开始准备，不等到开发完成才想。
6. 不做没有依据的精确时间承诺。

## 工作流程

### 1. 确认上线基线

从 PRD 和审查报告中提取：

- **版本范围**：本次上线包含哪些功能、页面、接口。
- **依赖项**：依赖的外部系统、第三方服务、数据就绪状态。
- **已知风险**：审查报告中标记的高风险项。
- **成功信号**：PRD 中定义的指标或行为信号。
- **历史数据**：是否需要迁移，迁移规模多大。
- **配置变更**：是否涉及后台配置、权限变更或内容更新。
- **用户影响**：是否影响现有用户的使用习惯或数据。

### 2. 设计灰度策略

| 维度 | 选项 |
|------|------|
| 发布类型 | 全量 / 百分比灰度 / 指定用户白名单 / 按机构层级 |
| 灰度比例 | 使用项目确认的阶段比例；无依据时列为待确认，不照搬固定节奏 |
| 观察窗口 | 每级灰度至少观察 X 小时/天 |
| 放量条件 | 核心指标正常 + 无 S0/S1 告警 + 用户反馈无重大问题 |
| 触发条件 | 回滚触发条件、暂停灰度条件 |

组织型或内部工具产品可按组织单元、角色或场景逐步扩大试点范围；具体层级、样本量和节奏必须依据当前组织结构、风险和监控能力确定。

### 3. 定义配置开关

每个功能开关至少说明：

| 字段 | 内容 |
|------|------|
| 开关名称 | 唯一标识 |
| 控制范围 | 控制哪个功能或页面 |
| 默认值 | 上线时的初始状态（开/关） |
| 配置位置 | 后台配置页 / 配置文件 / 环境变量 |
| 生效方式 | 实时生效 / 需重新部署 / 需清理缓存 |
| 紧急关闭流程 | 谁可以操作、几步完成、是否需要审批 |
| 关闭后的用户体验 | 隐藏入口 / 展示维护提示 / 降级方案 |

### 4. 制定回滚方案

| 维度 | 说明 |
|------|------|
| 回滚触发条件 | 具体的、可自动或人工判断的条件（如"核心接口错误率 > 5% 持续 5 分钟"） |
| 回滚决策人 | 谁有权决定回滚 |
| 回滚步骤 | 操作顺序（开关关闭 → 版本回退 → 数据修正 → 通知） |
| 数据回滚范围 | 上线期间产生的新数据如何处理 |
| 回滚后的用户通知 | 是否需要通知、通知渠道、通知文案 |
| 恢复时间目标 | 从决定回滚到恢复正常服务的目标时间 |

### 5. 定义监控指标与告警

#### 业务指标（验证价值）

| 指标 | 数据来源 | 预期范围 | 观察周期 | 异常条件 |
|------|----------|----------|----------|----------|
| | | | | |

#### 技术指标（验证稳定性）

| 指标 | 数据来源 | 正常范围 | 告警阈值 | 告警级别 |
|------|----------|----------|----------|:--:|
| | | | | |

告警通知对象和方式：谁通过什么渠道收到什么级别的告警。

### 6. 责任分工与沟通计划

| 角色 | 负责人 | 上线前 | 上线中 | 上线后 |
|------|:--:|------|------|------|
| 产品 | | 确认验收通过 | 关注业务指标 | 收集用户反馈 |
| 研发 | | 代码冻结、部署准备 | 监控技术指标 | 修复 Bug |
| 测试 | | 回归测试完成 | — | — |
| 运营 | | 内容/配置就绪 | 关注用户反馈 | 处理用户问题 |
| 数据 | | 埋点验证 | 数据就绪 | 输出数据报告 |

沟通计划：
- 上线前通知：什么时候、通知谁、通知什么内容。
- 上线中同步：灰度每阶段完成后通知谁。
- 异常升级路径：什么人 → 什么条件 → 升级到谁。

### 7. 输出上线检查清单

#### 上线前

- [ ] PRD 已通过评审
- [ ] 测试回归通过
- [ ] 埋点已验证
- [ ] 功能开关已配置
- [ ] 回滚方案已确认
- [ ] 监控告警已配置
- [ ] 历史数据迁移已完成（如适用）
- [ ] 运营配置/内容已就绪
- [ ] 用户通知已发送（如适用）
- [ ] 值班人员已确认

#### 上线中

- [ ] 开关已开启（或灰度已启动）
- [ ] 业务指标正常
- [ ] 技术指标正常
- [ ] 无 S0/S1 告警
- [ ] 灰度每阶段放量决策已记录

#### 上线后

- [ ] 全量稳定运行超过 X 小时/天
- [ ] 用户反馈已收集
- [ ] 数据报告已输出
- [ ] 后续优化项已记录
- [ ] 功能开关可清理（达到稳定后）

## 输出结构

### 《上线发布计划》

1. **版本信息**：版本号、上线范围、PRD 引用、审查报告引用。
2. **灰度策略**：发布类型、灰度节奏、放量/回滚条件。
3. **配置开关清单**：每个开关的名称、控制范围、默认值、紧急关闭流程。
4. **回滚方案**：触发条件、决策人、步骤、数据回滚、用户通知。
5. **监控与告警**：业务指标 + 技术指标、告警规则、通知对象。
6. **责任分工与沟通**：各角色职责、时间安排、升级路径。
7. **上线检查清单**：上线前/中/后检查项。

## 输出要求

- 默认使用中文。
- 灰度比例和观察窗口用具体数字，不写"适当""逐步"。
- 回滚条件必须可操作判断。
- 监控指标对应当前版本的具体功能，不套用通用模板。
- 不承诺未与研发确认的技术排期。
- 不替代运维系统的实际配置。

## 质量检查

1. 灰度策略是否有明确的放量和回滚条件。
2. 每个功能开关是否有紧急关闭流程。
3. 回滚是否覆盖触发条件、步骤、数据回滚、用户通知。
4. 监控指标是否区分业务指标和技术指标。
5. 责任分工是否具体到人（或角色）。
6. 检查清单是否覆盖上线前/中/后全阶段。
7. 是否避免了空泛的"确保稳定""密切关注"等不可执行描述。

## 与其他 Skill 衔接

- PRD 未评审通过时，先使用 `review-requirement` 完成审查。
- PRD 中发布要求不完整时，返回 `write-prd` 补充。
- 上线计划确认后，按计划执行发布。
- 上线后观察期结束，进入 `iterate-review` 进行复盘。
- 本 Skill 不替代运维发布系统的实际操作。
