# 功能创意发散与创新审视

## 目标

在产品概念基线已经澄清的基础上，系统性地向外发散功能可能性，审视每一项创意的创新价值，输出一个经过初筛的功能创意池。

重点回答：

- 围绕核心用户和场景，还能衍生出哪些功能方向？
- 从不同视角（场景、角色、技术、情感、游戏化、社交）看，有哪些被忽略的机会？
- 每个方向是真正的创新，还是功能堆叠或视觉包装？
- 哪些创意值得进入方案设计，哪些应该暂缓或剔除？
- 最需要优先验证的创新假设是什么？

最终交付物为《功能创意池》，可供 plan-product 或 design-feature-solution 使用。它追求广度与洞察，不替代正式规划、优先级决策或执行方案。

## 工作边界

本 Skill 负责：

- 从 concept-discovery 承接概念基线（用户、场景、核心价值机制）。
- 使用多维发散框架探索功能可能性。
- 对每个创意进行创新价值审视。
- 初步筛选优先级（核心闭环 / 体验增强 / 未来探索 / 建议剔除）。
- 将结果整理为结构化的功能创意池，交付 plan-product。

本 Skill 不负责：

- 重新定义产品定位、用户群体或核心价值主张。
- 进行模块架构设计、MVP 范围划分或版本分期。
- 设计具体功能的流程、交互、规则或字段。
- 替代 concept-discovery 的访谈式澄清。
- 在没有概念基线的情况下凭空发散。

## 基本原则

1. 发散必须在确认的基线上进行——不偏离核心用户和已确认的核心价值。
2. 追求创意的多样性与实质差异，不求数量求质量。
3. 创新必须说明发生在哪个维度，解决什么真实问题。
4. 对每个创意保持同样的审视标准，不因"有趣"而跳过检验。
5. 明确区分创新与包装——改名、换图标、加标签不是创新。
6. 优先保留让用户获得新结果的能力，而非只是新页面或新入口。
7. 对当前阶段无法验证的创意，标记而非丢弃。
8. 输出控制在 6-8KB，比执行型 skill 更轻量。

## 工作流程

### 1. 确认发散基线

从 concept-discovery 或当前对话上下文中提取：

- **首要用户**：谁是最核心的使用者。
- **核心场景**：在什么时间、地点、触发条件下使用。
- **当前替代方案**：用户现在怎么解决这个问题。
- **核心价值机制**：产品通过什么方式把输入转化为结果。
- **已确认的功能方向**：输入需求中已经明确的功能。
- **关键约束**：资源、技术、合规、时间等已知约束。
- **品牌与体验原则**：当前项目的品牌人格、目标情绪、不希望出现的表达。

如果基线信息不完整，先做轻量补充（3-5 个关键问题），不回到完整的 discovery 访谈。

### 2. 多角度发散

依次从以下 6 个角度向外发散功能创意。对每个角度，根据适用性选择 2-4 个创意方向。跳过与当前产品明显无关的角度。

#### 角度 1：场景延展

核心场景的前、中、后各阶段还有什么未被满足的需求？

- **场景前置**：用户在进入核心场景之前需要什么准备、触发或引导？
- **场景中置**：核心体验过程中有什么降速、等待、困惑或中断时刻？
- **场景后置**：核心体验完成后，用户想分享、回顾、对比或采取什么后续行动？
- **场景链**：与核心场景相邻的其他高频场景是否可以衔接？

#### 角度 2：角色切换

如果切换观察视角，不同角色会有什么不同的需求？

- **使用者视角**：除了核心任务，还有什么辅助任务或情绪需求？
- **服务提供者视角**：为使用者提供服务的角色需要什么？
- **旁观者/同伴视角**：与使用者同行或受其影响的人需要什么？
- **管理者/决策者视角**：谁为这项体验付费或负责，他们关心什么结果？

#### 角度 3：技术赋能

AI、数据、算法或设备能力能带来什么传统方式做不到的结果？

- **减少输入**：能否通过识别、推断、预填减少用户输入？
- **智能匹配**：能否根据用户特征、历史或情境个性化推荐？
- **预测与提醒**：能否在用户意识到需要之前主动提供？
- **生成与创作**：能否为用户生成内容、方案或建议？
- **自动化**：能否把多步骤合并为一步或后台完成？

对每项技术赋能方向必须回答：不使用该技术时是否存在更简单可靠的方案？技术标签本身不是价值。

#### 角度 4：情感设计

在功能之外，什么让用户产生正向情绪或记忆点？

- **仪式感**：能否设计一个让用户期待或记住的时刻？
- **惊喜与幽默**：什么意外的小细节会让用户会心一笑？
- **掌控感**：用户什么时刻最焦虑或不确定，如何缓解？
- **成就感**：用户完成什么后感到"我做到了"，如何强化？
- **归属感**：什么让用户感到"这个产品懂我"？

情感设计必须附着在真实功能上，不能独立成为空壳入口。

#### 角度 5：游戏化

能否借鉴游戏机制提升参与度和持续性？

- **进度与反馈**：用户能看到什么进度变化、里程碑或成长轨迹？
- **挑战与目标**：能否设计渐进的挑战，让使用有方向感？
- **随机与惊喜**：能否通过不确定性制造期待（盲盒、抽签、每日彩蛋）？
- **收集与成就**：用户能收集、解锁或展示什么？

游戏化必须服务于核心任务，不能为游戏化而增加操作步骤。纯粹的数字、徽章、排行榜如果与核心价值无关，不算创新。

#### 角度 6：社交裂变

能否通过人与人之间的互动扩大价值？

- **分享与展示**：用户完成什么后自然地想分享？分享什么？
- **协作与互助**：多人一起使用能否产生比单人更好的结果？
- **比较与激励**：什么维度的对比是积极的而非制造焦虑的？
- **邀请与传播**：什么时刻用户有动机邀请他人？

如果当前项目已经明确由其他模块或平台统一承接社交能力，此处只做与当前功能有关的创意并标记依赖，不重复设计独立社交系统。

### 3. 形成功能创意清单

将发散结果整理为清单。每项创意至少包含：

| 字段 | 说明 |
|------|------|
| 创意名称 | 简短的功能方向名称 |
| 发散角度 | 来自上述哪个角度 |
| 一句话描述 | 谁在什么场景下获得什么结果 |
| 价值机制 | 通过什么方式产生价值（不是功能描述） |
| 创新维度 | 用户/场景/体验/机制/技术/渠道/商业模式 |
| 复杂度预估 | 低/中/高（用户操作复杂度 + 开发复杂度） |
| 与已有功能的关系 | 独立新功能 / 已有功能延展 / 取代已有功能 |

### 4. 进行创新性审视

对每项创意逐一检查：

1. **差异发生在哪个维度？** 用户、场景、体验、机制、技术、渠道还是商业模式？不能只说"综合创新"。
2. **解决了什么真实问题？** 如果去掉技术标签和视觉包装，用户为什么需要它？
3. **相比现有替代方式有什么实质变化？** 用户能多做什么、少做什么或得到什么新结果？
4. **是否增加了不必要的成本？** 用户多了一步操作？运营多了一项负担？开发增加了显著复杂度？
5. **与产品核心价值是否一致？** 这个创意是让核心闭环更紧，还是分散注意力？
6. **能否低成本验证？** 不用完整开发，怎么最快验证用户是否真的需要它？

将审视结果标注：

- ✅ **实质性创新**：有清晰的差异、价值可解释、与核心一致、可低成本验证
- ⚠️ **可能创新但需验证**：方向有趣但证据不足或验证成本高
- ❌ **包装型创新**：只是新名称、新入口或新视觉，没有实质差异
- ➡️ **交给其他模块**：已由当前项目中确认的其他模块或平台能力承接

### 5. 进行优先级初筛

| 层级 | 判定标准 | 后续动作 |
|:--:|------|------|
| **核心延伸** | 让核心闭环更完整、更流畅或更差异化；不增加显著复杂度 | 优先进入 plan-product |
| **体验增强** | 不改变核心闭环，但明显提升用户情感或使用意愿 | 在核心闭环后考虑 |
| **未来探索** | 方向有价值但依赖数据积累、用户规模或技术成熟 | 标记，后续版本再评估 |
| **建议剔除** | 创新性不足、偏离核心、成本过高或可通过已有功能替代 | 说明剔除理由 |

### 6. 输出功能创意池

```markdown
## 功能创意池

### 发散基线回顾
（简要复述用户、场景、核心价值机制、已确认方向、关键约束）

### 创意清单

| 编号 | 创意名称 | 角度 | 描述 | 创新审视 | 优先级 |
|------|----------|------|------|:--:|:--:|
| I-01 | ... | 场景延展 | ... | ✅/⚠️/❌ | 核心延伸 |
| ... | ... | ... | ... | ... | ... |

### 重点创意展开
（对优先级为"核心延伸"的 3-5 个创意做 2-3 句展开）

### 剔除项说明
（对"建议剔除"项简要说明剔除理由）

### 建议下一步
- 推荐进入 plan-product 的核心延伸创意
- 建议先做用户验证的假设
- 与现有功能可能冲突的点
```

## 对话与协作方式

1. 简短复述发散基线，确认理解正确。
2. 根据产品特征选择 3-4 个最有价值的角度进行发散。
3. 每个角度给出 2-4 个创意方向，等待用户反馈。
4. 用户可以指出偏好的方向、要求深入某个角度、或者补充自己的创意。
5. 对用户特别感兴趣的方向，快速做更细化的发散。
6. 汇总输出功能创意池。

用户要求"再多想想"时，切换一个还没有深入的角度。用户认为某个方向"普通"时，追问该方向下"最极端/最大胆/最不可行"的版本是什么，往往能打开新局面。

## 输出要求

- 默认使用中文，先给基线确认，再发散，最后汇总。
- 每个创意用一句话说清"谁在什么场景获得什么结果"。
- 不把技术标签（AI、区块链、元宇宙）当作创新证据。
- 不把功能命名、图标选择或视觉风格当作创新。
- 不以数量代替质量；10 个经过审视的创意优于 30 个未审视的列举。

## 质量检查

1. 是否确认了发散基线再开始发散。
2. 是否从多个角度进行了发散，而不是只从一个角度。
3. 每项创意是否有明确的发散角度和价值机制。
4. 每项"实质性创新"是否能说清差异发生在哪个维度。
5. 是否有创意被错误地标记为创新（只是包装变化）。
6. 是否有一项"建议剔除"并说明了理由。
7. 是否给出了明确的下一步建议。
8. 输出是否控制在 6-8KB。
9. 是否避免了把不同产品的事实混入当前创意。

## 与其他 Skill 衔接

- 概念基线不清晰时，回到 `product-concept-discovery` 做快速基线确认。
- 需要模块收敛、正式优先级和 MVP 范围定义时，进入 `plan-product`。
- 某个核心延伸创意已经足够明确时，可跳过 plan-product，直接进入 `design-feature-solution`。
- 用户只是想"头脑风暴一下"而不需要后续规划时，可以只输出创意清单。
- 本 Skill 不做执行型 PRD；不替代 `write-prd`。
