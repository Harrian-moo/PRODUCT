# 产品功能方案设计

## 目标

将产品规划中已经确定的重点模块、MVP能力或待解决问题，转化为逻辑成立、体验清晰、范围可控的功能方案。

重点回答：

- 这个功能为什么需要存在，解决谁在什么场景下的什么问题。
- 用户通过什么机制获得什么结果。
- 存在哪些实质不同的方案，为什么推荐其中一个。
- 核心流程、功能结构、信息和交互策略如何配合。
- 哪些业务规则、状态和依赖会决定方案是否成立。
- 如何用较低成本验证价值和可用性。
- 哪些结论已经足以进入执行型PRD，哪些仍需确认。

最终交付物默认为《功能方案设计 V0.7》。它用于完成方案评审和产品决策，是产品规划与执行型PRD之间的桥梁，不是可直接交付研发的完整需求文档。

## 工作边界

本Skill负责：

- 功能目标、目标用户、核心场景和用户任务。
- 功能在产品旅程、模块架构和价值闭环中的位置。
- 现有方式、用户阻力和方案必要性判断。
- 方案原则、候选方案比较、推荐方案与取舍。
- 功能核心机制和端到端用户流程。
- 功能能力、子功能和模块关系。
- 信息层级、关键交互机制和反馈策略。
- 影响方案成立的关键业务规则和状态概览。
- AI、数据、内容、运营和跨系统的业务闭环。
- 本功能的首期范围、非范围、复杂度、风险和验证方式。
- 进入执行型PRD所需的决策和输入清单。

本Skill不默认负责：

- 整体产品定位、完整产品架构、路线图和跨产品优先级。
- 高保真原型、视觉稿、设计系统或像素级页面说明。
- 完整字段字典、输入校验、权限矩阵和状态转换表。
- 接口参数、错误码、数据库结构和技术架构。
- 穷举全部异常、边界、降级和测试场景。
- 完整验收标准、测试用例、研发排期和工时估算。

只补充当前方案决策所必需的执行细节。用户已经要求研发级定义时，完成必要的方案确认后转入执行型PRD工作流。

## 基本原则

1. 先验证功能必要性，再设计功能形态。
2. 从用户任务和结果出发，不从页面、按钮或技术能力出发。
3. 先设计端到端价值闭环，再拆分功能和页面。
4. 候选方案必须在机制、体验、价值、成本或风险上存在实质差异。
5. 推荐方案时同时考虑用户价值、业务价值、使用复杂度、运营成本、开发复杂度和验证成本。
6. 优先减少用户输入、选择、跳转和理解成本，让系统承担可控的复杂处理。
7. 创新必须产生真实改善，不把功能组合、名称变化、视觉包装或AI标签当作创新。
8. 只定义影响方案取舍的关键规则，不用大量执行细节掩盖方案尚未成立。
9. 区分事实、已确认决策、分析判断、产品建议、假设和待确认项。
10. 保持项目事实隔离，不自动继承其他产品的用户、品牌、规则和技术条件。

## 工作流程

### 1. 读取方案输入

按需读取：

- 当前项目最新的产品规划、概念型PRD和已确认决策。
- 当前模块所属版本、MVP范围、优先级和非范围。
- 用户研究、反馈、数据、业务流程和现有产品资料。
- 品牌、体验、技术、数据、运营、隐私和合规约束。
- `context/collaboration-preferences.md`，若文件存在。

只读取与当前模块或问题直接相关的资料。历史案例和其他产品只能用于参考方法，不得作为当前产品事实。

提取并区分：

- 已确认事实和决策。
- 用户提供但尚未验证的信息。
- 外部证据。
- 当前假设。
- 约束和依赖。
- 文档冲突与待确认项。

### 2. 执行方案成熟度检查

开始设计前，至少检查：

1. 当前要设计的是问题、用户任务、模块还是已经预设的功能。
2. 目标用户和首要场景是否明确。
3. 用户当前怎样完成任务，主要阻力是什么。
4. 期望产生的用户结果和业务结果是什么。
5. 该功能在核心旅程和价值闭环中的位置是什么。
6. 本期范围、非范围和上游规划决策是否明确。
7. 已知的业务、品牌、运营、技术、数据和合规约束是什么。

将成熟度判断为：

- **不宜设计**：用户、问题、目标结果或模块边界仍不清晰。
- **假设型方案**：可以探索机制，但关键需求或价值缺少证据。
- **可选型方案**：目标、场景和边界基本明确，可以比较方案并做出推荐。
- **可进入PRD**：推荐方案、核心流程、关键规则和范围已经确认。

若不宜设计：

- 定位和价值仍不清晰时，返回 `product-concept-discovery`。
- 模块、MVP或版本范围仍不清晰时，返回 `plan-product`。
- 用户问题缺少证据时，优先开展用户研究或需求验证。

假设型方案可以继续，但必须标记关键假设、验证方式以及假设失败后受影响的内容。

### 3. 建立方案基线

用简洁结构确认：

```markdown
### 方案基线
- 方案对象：
- 所属产品/模块：
- 所属阶段/版本：
- 目标用户：
- 核心场景：
- 当前方式与问题：
- 目标结果：
- 价值闭环位置：
- 本期范围：
- 非本期范围：
- 关键约束：
- 已有证据：
- 关键假设：
```

修改已有功能时，额外说明：

- 修改前的流程和规则。
- 需要改变的具体问题。
- 受影响的角色、页面、数据和上下游能力。
- 必须保持兼容的既有行为。

发现规划、历史文档和最新要求冲突时，指出冲突并请求确认，不得默默拼接。

### 4. 判断功能必要性

不要把用户提出的功能名称直接当作解决方案。先回答：

- 如果不做这个功能，用户会怎样完成任务。
- 当前替代方式的主要成本和损失是什么。
- 问题能否通过流程、规则、内容、运营或现有能力优化解决。
- 新功能是否进入真实使用链条，而不是孤立入口。
- 用户为什么愿意开始使用并持续使用。
- 功能结果是否会进入用户或业务的下一步行动。
- 该问题是否值得在当前阶段解决。

若更简单的方案能够达到目标，明确提出并说明取舍。若功能价值不足，建议暂停、缩小或重新定义，不为了完成文档而包装方案。

### 5. 定义用户场景和任务

围绕首要场景描述：

- 触发条件：什么事件或需求让用户开始。
- 用户动机：用户此刻想完成什么。
- 前置条件：开始前必须具备什么。
- 用户任务：用户需要作出哪些关键动作或判断。
- 系统职责：系统应减少什么成本并提供什么结果。
- 完成结果：用户如何知道任务完成。
- 后续动作：结果如何进入下一步骤或持续价值闭环。

优先形成1条核心场景，必要时补充差异明显的次要场景。不要在方案尚未确认时穷举所有异常场景。

需要用户故事时，使用：

```text
作为〔角色〕，
当〔触发场景〕时，
我希望〔完成任务或获得结果〕，
从而〔产生用户或业务价值〕。
```

不要把页面操作步骤伪装成用户价值。

### 6. 定义方案原则

根据当前产品和场景形成3至5条能够指导取舍的原则，例如：

- 优先让用户看到结果，再要求补充信息。
- 保持首要任务路径短而单一。
- 对复杂信息采用渐进披露。
- 关键决定允许确认、撤销或修改。
- 高风险结果必须解释并由用户或专业人员确认。
- 自动化失败时提供明确的人工或规则兜底。

原则必须来自当前目标、用户和约束。不得把示例机械套入所有产品。

### 7. 形成候选方案并完成取舍

存在实质不同的实现路径时，提供2至3个候选方案。每个方案至少说明：

- 核心机制。
- 用户怎样完成任务。
- 产生什么结果。
- 适用前提。
- 主要优势和损失。
- 关键依赖和风险。

按需比较：

| 维度 | 需要判断的内容 |
|---|---|
| 用户价值 | 是否更直接地产生目标结果 |
| 使用复杂度 | 输入、步骤、判断和学习成本 |
| 业务价值 | 是否进入业务闭环并可持续 |
| 体验一致性 | 是否符合品牌和整体产品体验 |
| 运营成本 | 内容、配置、审核和人工维护 |
| 开发复杂度 | 数据、系统、算法和第三方依赖 |
| 验证成本 | 能否低成本证明核心假设 |
| 风险 | 隐私、安全、合规和错误后果 |

给出推荐方案、推荐理由和不选择其他方案的原因。说明在什么条件变化时应改选其他方案。

不存在真实替代方案时，不为了形式强行制造多个选项；直接说明关键取舍。

### 8. 设计核心机制和价值闭环

使用以下链路检查方案：

```text
触发与输入
→ 系统处理或关键判断
→ 结果与反馈
→ 用户或业务采取行动
→ 产生可观察价值
→ 数据或反馈支持下一次改进
```

逐项说明：

- 输入从哪里产生，由谁提供。
- 系统承担什么处理，用户保留什么判断。
- 输出是什么，是否清晰、可信和可采用。
- 输出由谁使用，进入哪个下一动作。
- 完成一次任务后，为什么还会再次使用。
- 无法形成闭环的环节应如何简化、补足或移除。

不要把“生成内容”“展示结果”或“发送提醒”本身当作价值完成。

### 9. 设计端到端核心流程

至少覆盖：

```text
入口与触发
→ 前置判断
→ 核心操作
→ 系统处理
→ 结果反馈
→ 结果使用
→ 后续动作或再次进入
```

对每个关键节点说明：

- 哪个角色执行。
- 用户知道什么、需要判断什么。
- 用户采取什么动作。
- 系统如何响应。
- 失败或中断时如何返回可继续状态。
- 下一步是什么，是否存在断头路。

流程复杂或存在分支、循环和状态变化时，使用简洁流程图或状态图。图示用于表达逻辑，不替代规则说明。

### 10. 建立功能结构

从能力和价值拆分功能，不从页面数量拆分。至少区分：

- 核心能力：没有它就无法完成首要任务。
- 支撑能力：帮助理解、配置、管理或恢复。
- 延伸能力：提升频次、个性化或规模化，但不影响首期闭环。

对每项能力说明：

- 服务的角色和场景。
- 解决的问题和产生的结果。
- 在核心流程中的位置。
- 依赖的输入、能力或上下游模块。
- 首期是否必须真实成立。

识别重复能力、职责重叠、孤立功能和只增加复杂度的辅助功能。

### 11. 设计信息与交互策略

在不进入高保真设计的前提下，定义：

- 用户在每个阶段最需要看到的信息。
- 主要对象、信息层级和呈现顺序。
- 核心操作、次要操作和危险操作。
- 哪些信息应默认展示，哪些应渐进披露。
- 系统处理中的等待、进度和反馈方式。
- 成功、失败、空结果、不可用和无权限时的基本去向。
- 返回、取消、撤销、修改和再次进入的体验策略。
- 多端、特殊人群或无障碍要求（适用时）。

让交互策略符合当前项目的品牌人格、目标情绪和语言风格，不预设所有产品都需要游戏化、IP化或对话式入口。

### 12. 定义关键业务规则和状态

只定义影响方案选择、流程闭环或范围判断的关键内容：

- 进入条件和适用对象。
- 核心数据或内容的来源和归属。
- 创建、修改、删除、取消和恢复的原则。
- 核心状态、进入条件、退出条件和可执行动作。
- 排序、推荐、匹配、额度、频率或优先级原则。
- 角色之间的查看、操作和确认关系。
- 时间边界、历史记录和跨版本影响。
- 失败、重复、冲突或不可用时的总体处理策略。

对尚未确认的规则标记待确认项。不要在缺乏业务和技术依据时编造精确阈值、算法、字段和错误码。

### 13. 审查AI、数据、内容、运营和系统闭环

涉及AI时，至少回答：

1. 输入数据来自哪里，是否足够可靠。
2. AI替代或增强了哪个传统步骤。
3. 输出由谁使用，进入什么下一动作。
4. 用户如何理解、确认、修改或拒绝输出。
5. 错误、不确定或不可用时如何兜底。
6. 是否需要人工审核、专业判断或责任边界。
7. 不使用AI时是否存在更简单可靠的方案。

涉及数据时，说明数据来源、使用目的、更新方式、输出去向、授权和责任方。

涉及内容时，说明内容来源、生成、审核、更新、下架和质量责任。

涉及运营时，说明配置、审核、维护、客服、冷启动和异常处理责任。

涉及跨系统或第三方服务时，只定义业务触发、数据方向、时效、失败影响和验收目标，不擅自指定技术实现。

### 14. 控制范围、复杂度和风险

在当前规划范围内区分：

- **首期必须**：构成核心闭环或验证关键假设。
- **首期增强**：明显改善体验，但可在核心闭环后补充。
- **后续考虑**：依赖使用数据、规模或其他模块成熟。
- **明确不做**：与当前目标无关、成本过高或风险不可控。

识别主要复杂度来源：

- 用户步骤和认知负担。
- 角色、规则、状态和权限数量。
- 内容和运营维护。
- 数据质量和历史兼容。
- AI、算法、接口和第三方依赖。
- 隐私、安全、合规和专业责任。

优先通过减少输入、合并步骤、限制首期场景、人工验证或复用能力降低复杂度。不得用模糊规则掩盖复杂度。

### 15. 设计验证方式

让验证方式对应方案中的关键假设：

- 价值假设：用户是否愿意开始并采用结果。
- 可用性假设：用户能否理解并完成核心流程。
- 机制假设：输入、处理、输出和后续行动能否闭环。
- 可行性假设：数据、运营、系统或AI能力是否能够支持。
- 风险假设：错误、隐私或高风险后果是否可控。

按需选择概念原型、可点击原型、人工服务、规则模拟、技术验证、可用性测试或小范围试点。

定义可观察的行为或结果信号，不在缺少基线和数据时制造精确指标。说明验证失败后应调整、缩小还是停止什么。

### 16. 形成方案决策和PRD交接

方案讨论结束时，明确：

- 推荐方案和主要取舍。
- 已确认的目标、场景、流程、范围和规则。
- 被否决或暂缓的方案及原因。
- 仍需用户、业务、设计、研发、数据、运营或合规确认的问题。
- 需要先完成的原型、研究或技术验证。
- 进入执行型PRD所需补齐的输入。

只有以下内容基本明确时，才建议进入执行型PRD：

- 首要场景和用户目标。
- 推荐方案和核心机制。
- 端到端核心流程。
- 首期范围与非范围。
- 影响实现的关键规则和状态。
- 主要依赖、风险和未决事项。

不要用“方案文档已完成”代替方案已被确认。

## 对话与协作方式

遵循以下默认节奏：

1. 简短复述方案基线和成熟度。
2. 先提供一个可修改的初步机制或流程框架。
3. 存在真实选择时，再提供2至3个差异明确的候选方案。
4. 每轮只提出3至5个最可能改变价值、机制、流程或范围的问题。
5. 根据用户反馈更新共识、假设、方案取舍和待确认项。
6. 用户确认主要方向后再形成完整方案文档。

用户要求先看草案时，可以输出假设型方案，但要标明哪些内容不可直接写入执行型PRD。

用户认为方案“传统”“普通”“复杂”或“鸡肋”时，重新检查功能必要性、用户动机、结果是否可采用、价值闭环和更简单替代方案，不只修改名称、文案或视觉表现。

用户只要求核心流程、方案比较、AI机制、功能结构或风险分析时，只输出该部分及必要上下文。

## 《功能方案设计 V0.7》结构

根据任务复杂度选择必要章节，不为填满模板而编造信息。

1. **文档信息**：产品、模块、版本、方案成熟度、日期、责任人、输入文档和本版目标。
2. **执行摘要**：推荐方案、目标结果、核心机制、首期范围、最大假设和当前建议。
3. **方案基线**：目标用户、核心场景、现有方式、问题、价值闭环位置、约束、证据和假设。
4. **功能目标与非目标**：用户结果、业务结果、成功信号以及本次不解决的问题。
5. **用户场景与任务**：触发、动机、前置条件、核心任务、完成结果和后续动作。
6. **方案原则**：3至5条能够指导机制和体验取舍的原则。
7. **候选方案与决策**：方案差异、适用前提、比较、推荐理由和改选条件。
8. **推荐方案核心机制**：输入、处理、输出、采用、反馈和持续价值闭环。
9. **端到端核心流程**：角色、关键节点、系统响应、主要分支、中断恢复和下一步。
10. **功能结构**：核心、支撑和延伸能力，以及职责、价值、优先级和依赖。
11. **信息与交互策略**：信息层级、关键操作、渐进披露、反馈和基本状态策略。
12. **关键规则与状态概览**：进入条件、核心规则、主要状态、角色关系和总体异常策略。
13. **AI、数据、内容、运营和系统闭环**：只保留当前方案适用的部分。
14. **首期范围与非范围**：首期必须、首期增强、后续考虑和明确不做。
15. **复杂度、依赖与风险**：主要来源、影响、简化方式、验证或兜底措施。
16. **验证计划**：关键假设、验证方法、观察信号和失败后的调整方向。
17. **方案决策与PRD交接**：已确认项、待确认项、责任人、前置工作和下一份交付物。

## 输出要求

- 默认使用中文，结论优先，结构清晰。
- 按“已确认 / 假设 / 分析判断 / 产品建议 / 待确认”区分重要内容。
- 先说明功能价值、推荐机制和关键取舍，再展开流程与结构。
- 流程、图表和方案比较只在能够显著提升理解时使用。
- 功能描述必须说明角色、场景、动作、系统结果和后续价值。
- 方案比较必须包含实质差异、损失和推荐条件。
- 修改已有功能时，优先使用“修改前 / 修改后 / 影响范围”。
- 不制造精确市场数据、用户数据、指标目标、成本和排期。
- 不擅自承诺AI、接口、算法、数据和第三方能力。
- 不把功能清单、页面列表或创意描述当作完整方案。
- 不提前写入与方案决策无关的研发执行细节。

## 质量检查

输出前确认：

1. 是否说明功能为什么需要存在，而不只是怎样实现。
2. 是否有一个明确的首要用户、场景和目标结果。
3. 是否说明当前替代方式和新方案的真实改善。
4. 方案是否进入产品的核心旅程和价值闭环。
5. 候选方案是否存在实质差异，并给出明确推荐。
6. 核心机制是否覆盖输入、处理、输出、采用和反馈。
7. 端到端流程是否完整，是否存在断头路。
8. 功能结构是否围绕能力和价值，而不是页面堆叠。
9. 信息与交互策略是否降低用户操作和理解成本。
10. 关键规则和状态是否足以支撑方案评审。
11. AI、数据、内容和运营是否形成真实闭环并具备兜底。
12. 是否明确首期范围、非范围和复杂度控制方式。
13. 是否识别重大业务、技术、数据、隐私、安全和合规风险。
14. 验证方式是否对应关键假设。
15. 是否区分事实、假设、建议和待确认项。
16. 是否过早进入完整字段、接口、异常枚举和验收标准。

## 与其他Skill衔接

- 产品定位、首要用户、核心问题或价值主张仍不清晰时，使用 `product-concept-discovery`。
- 整体架构、模块边界、MVP范围、优先级或版本分期仍不清晰时，使用 `plan-product`。
- 用户需求、使用动机或方案价值缺少证据时，进入用户研究或需求验证工作流。
- 需要核实竞品机制、替代方案或行业惯例时，进入市场与竞品分析工作流。
- 方案机制和流程需要快速验证时，进入原型设计或可用性测试工作流。
- 目标、范围、流程、关键规则和状态已经确认后，进入执行型PRD工作流。
- 已有功能上线后需要依据数据和反馈优化时，进入产品分析或迭代优化工作流。

本Skill只负责把已规划的重点能力转化为可决策的功能方案，不替代上游产品规划，也不替代下游研发执行文档。
